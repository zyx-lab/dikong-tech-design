# 低空平台权限系统设计（V3 / 当前正式实现）

## 0. 设计目标
1. 正式权限与身份接口统一进入 `/api/v1/iam/*`，不再保留 `/internal/auth/*` 正式入口。
2. 正式 API 统一采用 Bearer Token，会话由 `AuthSession` 承载。
3. 租户工作态与平台工作态严格分层，路径决定作用域，不再让同一路径随调用者身份改变语义。
4. 保持 RBAC 核心：`TenantMember -> TenantMemberRole -> RolePermissionGrant -> Permission`。
5. 保持白名单权限策略：只启用显式权限码，不使用模型默认 CRUD 权限。

## 1. 接口平面边界
1. 正式 IAM 平面
- URL 前缀：`/api/v1/iam/*`
- 文档入口：`/api/v1/docs/`
- 子作用域：
  - `session/*`
  - `me/*`
  - `tenant/*`
  - `platform/*`

2. 业务平面
- URL 前缀：`/api/v1/*`
- 文档入口：`/api/v1/docs/`
- 能力：无人机、任务、飞行记录、媒体等业务资源

3. 统一文档
- 文档入口：`/api/v1/docs/`
- Schema：`/api/v1/docs/schema/`
- 当前只聚合正式 `/api/v1/*` 接口

## 2. 核心模型
1. `User -> StaffProfile (1:1)`：全局账号与全局人员档案。
2. `Tenant`：租户实体。
3. `Tenant -> TenantMember (1:N)`：账号加入租户后形成成员关系。
4. `TenantMember -> TenantMemberRole (1:N)`：成员在租户内被授予业务角色。
5. `TenantMemberRole -> Role (N:1)`：角色来自平台统一角色目录。
6. `Role -> RolePermissionGrant -> Permission`：角色绑定默认权限模板与 scope。
7. `TenantMember -> TenantMemberQualification (1:N)`：成员资质记录。
8. `AuthSession`：正式 Bearer 会话。

字段边界：
1. `User` 只承载账号域字段，如 `username / password / status / is_platform_admin`。
2. `StaffProfile` 只承载全局人员事实信息，如 `name / phone / email / employment_status / org_id`。
3. 租户内显示名、工号、角色等都放在 `TenantMember` 或其子表，不回写 `User / StaffProfile`。
4. `member_no` 是租户内编号，不是全局人员编号。

## 3. 鉴权计算链

### 3.1 正式 IAM 运行态

`允许 = 账号状态通过 AND 运行态匹配 AND 权限命中 AND scope命中 AND 业务状态机通过`

当前运行态：
1. `unassigned`
2. `tenant_member`
3. `platform_operator`

### 3.2 计算步骤
1. 校验账号状态：`is_active=True` 且 `status=ACTIVE`。
2. 若 `user.is_superuser=True`：视为技术 root，不进入正式 IAM 会话集合。
3. 若 `user.is_platform_admin=True`：进入 `platform_operator`。
4. 普通正式业务账号必须绑定 `StaffProfile`，然后根据是否存在租户成员关系判定为 `unassigned` 或 `tenant_member`。
5. `tenant/*` 请求在合法 `X-TENANT-CODE` 下解析当前租户与当前成员关系。
6. 从 `TenantMemberRole(GRANTED)` 命中角色。
7. 从 `RolePermissionGrant` 命中权限与 scope。
8. 对业务资源执行状态机与数据范围校验。

### 3.3 特殊主体
1. `superuser`
- 技术 root。
- 不属于正式 IAM 账号集合。
- 不通过 `session/login` 建立正式 Bearer 会话。

2. `platform_admin`
- 通过 `User.is_platform_admin=true` 承载。
- 只进入 `platform/*`。
- 不允许进入 `TenantMember` 链。

## 4. 关键数据表

| 表名 | 说明 |
|---|---|
| `auth_users` | 登录账号 |
| `staff_profiles` | 全局人员档案 |
| `tenants` | 租户主表 |
| `tenant_members` | 租户成员关系 |
| `roles` | 平台角色目录 |
| `permissions` | 平台权限目录 |
| `role_permission_grants` | 角色默认权限映射 |
| `tenant_member_roles` | 成员角色绑定 |
| `qualification_types` | 平台资质类型 |
| `tenant_member_qualifications` | 成员资质记录 |
| `auth_sessions` | Bearer 会话 |
| `auth_audit_logs` | 权限与关键变更审计 |

## 5. 强约束
1. 禁用 `user_permissions` 直配。
2. 禁用用户直绑 `Group`。
3. `superuser` 与 `platform_admin` 不能同时为 true。
4. `superuser` 不允许绑定 `StaffProfile`。
5. 非 `superuser` 的正式业务账号必须绑定 1 条 `StaffProfile`。
6. `platform_admin` 不允许成为 `TenantMember`。
7. `superuser` 不允许成为 `TenantMember`。
8. `TenantMember.member_no` 只在租户内唯一，不做全局唯一。
9. scope 合并规则固定：`ALL > ASSIGNED > OWN`。
10. 有权限但无合法 scope 配置，默认拒绝。
11. `OWN / ASSIGNED` 权限映射要求 `Permission.resource_code` 非空。
12. 租户成员角色只能使用平台角色目录中的可分配角色，不能分配 `platform_admin`。
13. 当前租户不得失去最后一个有效 `tenant_admin`。
14. 权限变更基线以 `seed_role_permissions.py` 为准。
15. 正式 API 不保留旧 `/internal/auth/*` 兼容层。

## 6. 命名规范
1. 角色机器码：`platform_admin`、`tenant_admin`、`business_admin`、`route_planner`、`dispatcher`、`pilot_operator`、`auditor`。
2. 平台管理权限码：`access.manage_*`、`access.view_*`。
3. 业务权限码：`<app_label>.<resource>_<action>`，如 `drone.view_drone`。
4. 正式 API 字段统一使用 camelCase，如 `tenantId`、`tenantCode`、`memberId`、`userId`。

## 7. 路由治理规范
1. 正式 IAM 接口只放 `/api/v1/iam/*`。
2. 业务接口只放 `/api/v1/*`。
3. `me/*` 只处理当前登录业务账号自己的全局资料。
4. `tenant/*` 只处理当前租户工作态，统一依赖 `X-TENANT-CODE`。
5. `platform/*` 只处理平台治理，不进入租户工作态。
6. 邀请流、`me/permissions`、`set-plan`、全局用户目录不再属于正式 API。

## 8. 初始化与运行
```bash
python manage.py migrate
python manage.py seed_role_permissions --mode replace
python manage.py createsuperuser
python manage.py create_business_admin_account --username biz_root --password 'YourStrongPassword'
python manage.py runserver
```

补充说明：
1. `create_business_admin_account` 只创建账号与 `StaffProfile`，不直接分配租户角色。
2. 如需实际业务权限，仍需为该账号创建 `TenantMember` 并分配租户角色。
