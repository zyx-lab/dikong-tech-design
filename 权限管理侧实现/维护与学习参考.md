这份文档面向接手维护同学，重点是“先看什么、改哪里、如何验证”。

## 1. 建议阅读顺序
1. [权限设计.md](权限设计.md)：先理解规则和边界。
2. [角色权限矩阵设计.md](角色权限矩阵设计.md)：再看默认角色配置。

## 2. 核心知识点（Django/DRF）
1. `auth_permission`
- Django 权限字典表，每条权限形如 `app_label.codename`。
- 本项目采用白名单权限（`default_permissions=()` + 显式 `Meta.permissions`）。

2. `Group`
- 这里把 Group 当“能力模块”，不是部门组织。
- 最终授权链是：`staff_type -> group -> permission(scope)`。

3. `User` 与 `StaffProfile` 的边界
- `User` 仅保存账号域信息（登录、启用、后台状态）。
- `User` 基于 `AbstractBaseUser + PermissionsMixin`，不复用 `AbstractUser` 的资料字段。
- `StaffProfile` 保存人员事实信息（name/phone/email/staff_type）。
- superuser 不允许绑定 staff；非 superuser 必须绑定 1 条 staff。
- superuser 作为 root 账号，默认拥有系统与业务全量权限。
- superuser 仅允许命令行创建（`createsuperuser`），禁止在 Admin/API 中升权。

4. DRF Permission Class
- `RequireInternalPermission`：内部 IAM 接口校验（superuser 可进，普通账号走 staff_type 权限）。
- `ScopedActionPermission`：业务接口动作校验（身份+权限+scope；superuser 直通）。
- `ScopedQuerysetMixin`：列表在 queryset 层做 scope 过滤。

5. m2m_changed 信号
- 用于强制禁止 `User.groups` 和 `User.user_permissions` 的直接改动。
- 目的是防止出现第二条绕过 staff_type 的授权路径。

## 3. 关键代码入口
1. 模型定义：`apps/access/models.py`
2. 鉴权服务：`apps/access/services.py`
3. 权限类：`apps/access/drf_permissions.py`
4. IAM API：`apps/access/views.py`
5. Admin 管理：`apps/access/admin.py`
6. 权限矩阵初始化：`apps/access/management/commands/seed_role_permissions.py`
7. 路由总入口：`config/urls.py`

## 4. 常见改动怎么做
1. 新增业务权限
- 在业务模型 `Meta.permissions` 声明权限码。
- `makemigrations` + `migrate`。
- 在 IAM 中配置 `group -> permission -> scope`。

2. 新增角色（StaffType）
- 新增 `staff_types` 记录。
- 配置 `staff_type_groups`。

3. 调整授权策略
- 优先改 `seed_role_permissions.py` 的基线矩阵。
- 执行 `python manage.py seed_role_permissions --mode replace`。

4. 创建业务管理员账号
- 先执行 `seed_role_permissions`，确保 `business_admin` staff_type 已存在。
- 执行 `python manage.py create_business_admin_account --username <账号> --password <密码>`。
- 注意：该账号是普通业务账号（非 Django superuser）。

## 5. 最小验证清单
1. `python manage.py check`
2. `python manage.py test apps.access`
3. 登录后访问：
- `/internal/docs/`（内部 IAM 文档）
- `/api/v1/docs/`（业务 API 文档）
4. 用普通业务账号验证：
- 直绑 `group` / `user_permissions` 会被拒绝
- `me/permissions` 能返回 scope 合并结果
