# 使用固定角色的单租户权限模型

重构项目采用单租户、无部门的固定角色权限模型，只保留平台管理员、业务管理员、飞手、任务监控调度员四类角色。每个用户只能被分配一个角色，角色定义由系统固定；不提供运行时创建角色、菜单权限或数据范围规则。已接入资源按角色全局可见，接口默认拒绝未明确允许的操作。这样可以移除当前动态 RBAC、部门数据范围和资源共享的复杂度，同时保持业务侧权限边界清晰。API 去留以 [API 功能范围](../api-scope.md) 为准。

## Consequences

- 每个接口的授权规则按固定角色定义，默认拒绝未授权操作。
- 系统只保留一个平台管理员账号 `root`，拥有全局系统治理和全部业务操作能力；业务管理员拥有业务侧管理能力，但不能创建、禁用或修改 `root`。
- 业务管理员之间平级，不能互相管理；业务管理员只能管理普通业务用户。
- 业务管理员只能创建飞手和任务监控调度员；新的业务管理员只能由 `root` 创建。
- 业务管理员的角色编码为 `business_admin`；其余角色编码尽量沿用原编码。
- `root` 使用普通登录接口登录，但账号创建和密码恢复走部署级流程。
- 用户删除统一表现为禁用，不做物理删除。
- 禁用用户立即撤销其全部认证会话；密码重置也立即撤销旧会话。
- 菜单查询接口保留，菜单定义随版本发布，不允许运行时编辑。
- 所有写操作和高风险操作写入审计日志，普通查询不写业务审计。
- DRC、资源解绑、任务中止等高风险操作不增加新的后端确认协议，由前端确认，后端负责权限、参数、状态、幂等和审计。
- 后续如果需要细粒度授权，需要新增明确的权限模型，而不是隐式扩展固定角色。
