# 低空平台权限系统设计（V3 / 双平面）

## 0. 设计目标
1. 账号与授权管理采用内部管理平面（Internal IAM Plane），不对公网暴露。
2. 业务功能采用对外业务平面（Business API Plane），用于业务 UI/客户端调用。
3. 保持 RBAC 核心：`StaffType -> Group -> Permission(+Scope)`。
4. 保持白名单权限策略：只启用显式权限码，不使用模型默认 CRUD 权限。

## 1. 双平面边界
1. 内部管理平面（IAM）
- URL 前缀：`/internal/auth/*`
- 文档入口：`/internal/docs/`
- 能力：账号、StaffType、Group、Scope、审计
- 暴露策略：仅内网/VPN/网关白名单

2. 业务平面（Business）
- URL 前缀：`/api/v1/*`
- 文档入口：`/api/v1/docs/`
- 能力：无人机、任务、飞行记录等业务资源
- 暴露策略：按业务发布策略对外开放

## 2. 核心模型
1. `user -> staff_profile (1:1)`：一账号一 Staff。
2. `staff_profile -> staff_type (N:1)`：身份分类。
3. `staff_type -> groups (M:N)`：身份类型组合能力模块。
4. `group -> permissions (M:N)`：能力模块包含权限点。
5. `group + permission -> scope`：权限点绑定数据范围（`ALL/ASSIGNED/OWN`）。

字段边界：
1. `User` 只承载账号域字段（登录名、密码、启用状态、后台状态）。
2. `name/phone/email` 等人员事实字段统一放 `StaffProfile`，不放 `User`。
3. `User` 采用 `AbstractBaseUser + PermissionsMixin` 实现，避免 `AbstractUser` 的冗余字段污染账号域。

## 3. 鉴权计算链
`允许 = 身份状态通过 AND 权限命中 AND scope命中 AND 业务状态机通过`

计算步骤：
1. 校验账号状态（`is_active + status`）。
2. 若 `user.is_superuser=True`：直接授予 `ALL`（root 语义），跳过 `staff_type -> group -> scope` 矩阵计算。
3. 若非 `superuser`：校验 staff 绑定、在职、staff_type 激活。
4. 从 `staff_type_groups` 取 Group。
5. 从 `auth_group_permissions` 命中权限。
6. 从 `auth_group_permission_scopes` 取有效范围并合并（`ALL > ASSIGNED > OWN`）。
7. 在业务资源上执行状态机校验（如任务状态、资质状态）。

## 4. 关键数据表
| 表名 | 说明 |
|---|---|
| `auth_users` | 登录账号 |
| `staff_profiles` | 人员档案（1:1 user） |
| `staff_types` | 身份类型 |
| `auth_group` | 能力模块 |
| `staff_type_groups` | 身份类型到能力模块 |
| `auth_permission` | 权限点字典 |
| `auth_group_permissions` | Group 到权限点 |
| `auth_group_permission_scopes` | Group+权限 的范围策略 |
| `auth_audit_logs` | 授权与关键变更审计 |

## 5. 强约束
1. 禁用 `user_permissions` 直配。
2. 禁用用户直绑 `Group`。
3. 非 `superuser` 账号必须且仅能绑定 1 条 `staff_profile`。
4. 非 `superuser` 参与业务鉴权时，必须满足：`staff_profile` 存在、`employment_status=ACTIVE`、`staff_type` 激活。
5. `superuser` 作为 root 账号，默认拥有系统与业务全量权限（含未来新增权限），不走 `staff_type` 矩阵，也不需要维护矩阵授权。
6. `superuser` 禁止绑定 `staff_profile`。
7. `superuser` 只能通过命令行创建（`createsuperuser`）；Admin/API 禁止设置或修改 `is_superuser`。
8. 白名单权限：`default_permissions=()`，仅保留显式定义权限码。
9. scope 合并规则固定：`ALL > ASSIGNED > OWN`。
10. 有权限但无 scope 配置，默认拒绝（`SCOPE_NOT_CONFIGURED`）。
11. 权限变更只允许三类入口：
- `staff_type_groups`
- `auth_group_permissions`
- `auth_group_permission_scopes`
12. 所有权限变更必须落审计日志。
13. 不保留旧版本兼容分支（不做旧机器码自动归并、不过渡清理接口）；结构变更通过重建库与重跑种子完成。

## 6. 命名规范
1. StaffType 机器码：`dispatcher_junior`、`pilot_operator`。
2. Group 展示名：`权限策略管理组`、`员工自助访问组`。
3. 管理权限码：`access.manage_*`、`access.view_*`。
4. 业务权限码：`<app_label>.<resource>_<action>`，如 `drone.view_drone`。

## 7. 路由治理规范
1. IAM 管理接口只放 `/internal/auth/*`，不放 `/api/v1/*`。
2. 业务接口只放 `/api/v1/*`，不混入 IAM 管理动作。
3. 文档拆分：
- IAM 文档：`/internal/docs/`
- 业务文档：`/api/v1/docs/`

## 8. 初始化与运行
```bash
python manage.py migrate
python manage.py seed_role_permissions --mode replace
python manage.py createsuperuser
python manage.py create_business_admin_account --username biz_root --password 'YourStrongPassword'
python manage.py runserver
```
