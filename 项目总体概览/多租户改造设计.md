# 低空平台多租户改造设计（最终定稿版）

## 1. 目标

将当前系统改造成可对外售卖的 SaaS 多租户系统。

本次定稿只确认以下约束：

1. 不同租户之间的数据必须严格隔离。
2. 买家不能自定义角色，角色由平台统一预置。
3. 每个租户必须有自己的管理角色 `tenant_admin`。
4. 平台默认不能查看租户业务数据。

---

## 2. 总体结论

本系统应改造成：

- 单库共享表的多租户系统
- 所有业务数据显式归属某个 `Tenant`
- 权限采用“平台固定角色 + 租户内分配”
- 平台管理面、租户管理面、业务使用面三层分离

不采用的方案：

- 不采用买家自定义角色
- 不采用每个租户单独一套权限模型
- 不采用平台管理员天然可看所有租户业务数据

---

## 3. 核心原则

### 3.1 租户是一等实体

买家就是 `Tenant`。所有业务数据都必须归属某个租户，不能再依赖零散的组织字段表达租户概念。

### 3.2 租户隔离先于业务权限

所有请求都必须先过租户边界，再进入角色、权限码、scope 判定。

授权顺序应为：

1. 解析当前租户
2. 校验当前用户是否属于该租户
3. 读取该用户在该租户内的固定角色
4. 计算该角色对应的权限与范围
5. 在当前租户内应用 `ALL / OWN / ASSIGNED`

### 3.3 固定角色由平台维护

角色由平台统一定义并初始化，买家只能在本租户内给成员分配固定角色，不能新增或修改角色模板。

### 3.4 平台不进入租户业务数据面

平台只管理租户、套餐、角色模板、权限目录、平台审计和系统运维；默认不能查看租户的业务明细数据。

---

## 4. 管理面划分

### 4.1 平台管理面

面向平台运营方。

职责：

- 创建和停用租户
- 初始化租户管理员
- 管理固定角色模板
- 管理全局权限码目录
- 管理套餐、配额、计费
- 查看平台级审计

限制：

- 默认不能查看租户业务数据

#### 4.1.1 superuser 的定位

> **概念区分**：
> - `superuser`：Django 系统级账号，技术概念，拥有所有技术权限（如创建模型、修改权限）
> - `platform_admin`：业务角色，用于平台运营管理，受业务权限系统约束

`superuser` 定位：

- 拥有平台管理面的所有权限
- 可以管理租户、角色模板、权限目录
- **不遵循** TenantMember 授权链路（绕过租户限制）
- 视为平台的 root 账号

> **说明**：`superuser` 与 `platform_admin` 是两个不同概念：
> - `superuser` = 技术实现（绕过业务权限系统）
> - `platform_admin` = 业务角色（受业务权限系统约束）

---

### 4.2 租户管理面

面向买家管理员，即 `tenant_admin`。

职责：

- 管理本租户成员（添加、移除、禁用）
- 给本租户成员分配固定角色
- 查看本租户审计
- **管理本租户所有业务数据**（无人机、航线、任务、飞行记录等）
- **是租户最高权限**，可操作租户内一切业务

限制：

- 不能访问其他租户
- 不能修改平台角色模板
- 不能修改全局权限码目录

> **说明**：`tenant_admin` 是租户最高权限，包含 `business_admin` 的所有业务权限。
> - `tenant_admin`：管人、管角色、管审计、管业务
> - `business_admin`：管业务（分工角色，由 tenant_admin 分配）

### 4.3 业务使用面

面向租户内的所有成员（包括各种业务角色）。

职责：

- 使用无人机、航线、任务、飞行记录、媒体等业务功能
- 根据固定角色（business_admin / route_planner / dispatcher / pilot_operator / auditor）获取相应业务权限

> **说明**：租户成员 = 租户内的全部人员（广义）。普通业务用户 = 租户成员中承担业务角色的那部分人（狭义，非管理员）。本节面向的是所有租户成员。

## 5. 核心模型

### 5.1 Tenant

租户主表，表示一个买家。

建议字段：

- `id`
- `code`
- `name`
- `status`
- `plan`
- `created_at`
- `updated_at`

### 5.2 User

平台登录账号，只负责认证。

#### 5.2.1 StaffProfile 的去留

现有的 `StaffProfile` 保留，作为**用户个人档案**：

- 不参与租户授权逻辑
- 存储用户的个人信息（姓名、工号、手机、邮箱）
- 与租户身份解耦
- 不再是租户成员的身份凭证

> **说明**：原来的 `StaffProfile` 承担了"租户身份"功能。本次改造后，租户身份功能迁移到 `TenantMember`，`StaffProfile` 只保留用户档案功能。

---

### 5.3 TenantMember

表示某个 `User` 在某个 `Tenant` 中的成员身份。

建议字段：

- `id`
- `tenant_id`
- `user_id`
- `display_name`
- `staff_no`
- `phone`
- `email`
- `status`
- `joined_at`
- `created_at`
- `updated_at`

说明：

- `TenantMember` 是租户内身份主体
- 成员管理、角色分配、创建人、指派关系都围绕 `TenantMember`
- 一个 `User` 可以有多个 `TenantMember`（属于不同租户）
- 一个 `TenantMember` 可以绑定多个角色

---

### 5.4 SystemRole

平台固定角色目录。

建议字段：

- `id`
- `code`
- `name`
- `description`
- `status`

### 5.5 TenantMemberRole

租户成员与固定角色的绑定关系。

建议字段：

- `id`
- `tenant_member_id`
- `system_role_id`
- `status`
- `created_at`
- `updated_at`

### 5.6 Permission / Group / Scope

以下模型继续保留为平台级模型：

- `Permission`
- `Group`
- `GroupPermissionScope`

绑定关系调整为：

- `SystemRole -> Group`

## 6. 固定角色

本系统共有 **7 个固定角色（SystemRole）**，由平台统一定义和维护。

> **概念说明**：
> - `superuser`：Django 系统级账号，**不是业务角色**
> - `SystemRole`：平台定义的固定角色模板，所有租户共用

**角色分类**：

| 分类 | 角色 | 说明 |
|-----|------|------|
| 平台级 | `platform_admin` | 平台运营，管理租户 |
| 租户级 | `tenant_admin` | 租户最高权限 |
| 租户级 | `business_admin` | 租户业务管理员 |
| 租户级 | `route_planner` | 航线规划 |
| 租户级 | `dispatcher` | 任务调度 |
| 租户级 | `pilot_operator` | 飞手 |
| 租户级 | `auditor` | 审计查看 |

角色定义：

- `platform_admin`：平台运营角色，只管理平台和租户，不进入租户业务数据面
- `tenant_admin`：租户最高管理角色，管理本租户成员、角色分配、审计和业务数据
- `business_admin`：租户内业务管理员，管理本租户全部业务数据
- `route_planner`：航线与航点规划
- `dispatcher`：任务调度
- `pilot_operator`：飞行执行
- `auditor`：审计查看

**各角色权限矩阵**：

| 角色 | 租户管理 | 成员管理 | 角色分配 | 租户审计 | 无人机 | 航线 | 航点 | 任务 | 飞行记录 | 媒体文件 | 无人机分配 |
|-----|:--------:|:--------:|:--------:|:--------:|:------:|:----:|:----:|:----:|:--------:|:--------:|:----:|
| platform_admin | ALL | - | - | - | - | - | - | - | - | - | - |
| tenant_admin | - | ALL | ALL | ALL | ALL | ALL | ALL | ALL | ALL | ALL | ALL |
| business_admin | - | - | - | - | ALL | ALL | ALL | ALL | ALL | ALL | ALL |
| route_planner | - | - | - | - | view | manage | manage | - | - | - | - |
| dispatcher | - | - | - | - | view | - | - | manage | - | - | manage |
| pilot_operator | - | - | - | - | view | - | - | view | manage | manage | - |
| auditor | - | - | - | - | view | view | view | view | view | view | view |

> **说明**：
> - `view`：查看权限
> - `manage`：新增/编辑权限
> - `ALL`：全部权限
> - `-`：无权限
> - **租户管理**：租户信息配置、套餐等（平台管理）
> - **成员管理**：添加/移除/禁用租户成员（租户内部管理）
> - **角色分配**：给成员分配/撤销角色（租户内部管理）
> - **租户审计**：查看本租户的操作审计日志（租户内部事务）
> - **platform_admin** 只管理租户本身，不介入租户内部事务
> - **auditor** 是租户内部角色，查看业务审计，不是租户管理审计

## 7. 权限体系改造

### 7.1 当前链路

当前系统的授权链是：

`user -> staff_profile -> staff_type -> group -> permission(scope)`

该设计的问题是：

1. 没有租户上下文
2. `staff_type` 同时承担身份类型和权限角色语义
3. 无法表达“租户内分配固定角色”

### 7.2 目标链路

新的授权链应为：

`user -> tenant_member -> tenant_member_role -> system_role -> group -> permission(scope)`

### 7.3 scope 语义

多租户后 scope 定义为：

- `ALL`：当前租户全部数据
- `OWN`：当前租户内自己创建的数据
- `ASSIGNED`：当前租户内分配给自己的数据

`ALL` 不再表示全平台全部数据。

### 7.4 Scope 机制设计

#### 7.4.1 核心原则

**过滤顺序不能颠倒**：

```
1. tenant_id 过滤（强制）→ 2. scope 过滤 → 3. 对象级检查
```

如果顺序颠倒，会导致跨租户数据泄露。

#### 7.4.2 实现方式

```python
# 错误示例（会导致数据泄露）
def get_queryset(self):
    if scope == ScopeType.ALL:
        return queryset  # 危险！返回全部数据（包括其他租户）

# 正确示例
def get_queryset(self):
    # 1. 先过滤租户
    queryset = queryset.filter(tenant_id=current_tenant_id)

    # 2. 再应用 scope
    if scope == ScopeType.ALL:
        return queryset  # 此时 queryset 已经被 tenant_id 过滤过
    if scope == ScopeType.OWN:
        return queryset.filter(created_by_member_id=current_member_id)
    if scope == ScopeType.ASSIGNED:
        return queryset.filter(assigned_member_id=current_member_id)
```

#### 7.4.3 租户上下文结构

```python
@dataclass
class TenantContext:
    tenant_id: int          # 当前租户 ID
    member_id: int          # 当前用户的 TenantMember ID
    roles: list[str]        # 当前用户的角色列表
```

### 7.5 多角色权限计算

一个 `TenantMember` 可以绑定多个 `SystemRole`，权限计算采用**优先级覆盖**方式。

**角色优先级（从高到低）**：

```
tenant_admin > business_admin > route_planner > dispatcher > pilot_operator > auditor
```

**计算规则**：

1. 收集当前 TenantMember 绑定的所有角色
2. 按优先级排序，取**最高优先级**角色的权限
3. 低优先级的角色权限被覆盖

**示例**：

```
TenantMember 绑定了: [pilot_operator, route_planner]
- pilot_operator 权限: [view_drone, pilot_mission]
- route_planner 权限: [view_route, manage_route]

因为 pilot_operator > route_planner
最终权限 = pilot_operator 的权限 = [view_drone, pilot_mission]
（route_planner 的权限被覆盖）
```

**场景说明**：

- 如果一个成员既是"飞手"又是"航线规划员"，系统只认更高优先级的角色权限
- 避免权限过于复杂导致的安全风险

## 8. 业务数据模型改造

所有业务核心表都必须显式增加 `tenant_id`：

- `drones`
- `routes`
- `waypoints`
- `missions`
- `flight_records`
- `media_files`
- `drone_assignments`
- `audit_logs`

同时建议统一增加：

- `created_by_member_id`
- `updated_by_member_id`

如存在"指派给谁"的语义，则使用：

- `assigned_member_id`

### 8.1 org_id 与 tenant_id 共存

现有系统中的 `org_id` 字段**保留**，作为后续扩展字段：

- 不参与租户隔离逻辑
- 可用于表达租户内的组织结构（如部门、班组）
- 不在本次改造范围内

---

## 9. 跨表约束

所有跨表引用都必须满足“同租户引用”。

必须成立的约束包括：

1. `Mission.route`、`Mission.drone`、`Mission.pilot_member` 必须属于同一 `tenant_id`
2. `FlightRecord.mission`、`FlightRecord.drone`、`FlightRecord.pilot_member` 必须属于同一 `tenant_id`
3. `Waypoint.route` 必须与 `Route` 同租户
4. `MediaFile.flight_record` 必须与 `FlightRecord` 同租户
5. `DroneAssignment.drone` 与 `DroneAssignment.member` 必须同租户

数据库层建议同时保证：

- 所有关键索引包含 `tenant_id`
- 所有唯一约束尽量改为租户内唯一

例如：

- `(tenant_id, code)`
- `(tenant_id, serial_no)`
- `(tenant_id, flight_no)`

## 10. 成员管理机制

### 10.1 账号主权

`User` 账号属于平台，不属于任何租户。

- 账号由平台统一管理
- 租户只能邀请用户加入，不能"创建"账号
- 离职后账号由平台回收或停用

### 10.2 成员加入方式

| 方式 | 说明 | 接口 |
|-----|------|------|
| **邀请制** | 租户管理员发送邀请，用户确认后加入 | `POST /api/access/tenants/{id}/members/invite/` |
| **直接添加** | 租户管理员直接添加已注册用户 | `POST /api/access/tenants/{id}/members/` |

### 10.3 注册接口

采用**平台注册 + 租户邀请**模式：

1. 用户在平台注册账号
2. 注册后账号处于"未激活"状态
3. 租户管理员邀请用户加入租户
4. 用户确认后成为租户成员，获得业务角色

```json
// POST /api/access/users/register/
{
  "username": "zhangsan",
  "password": "xxx",
  "name": "张三",
  "phone": "13800138000"
}

// 响应
{
  "business_code": "SUCCESS",
  "user_id": 1,
  "message": "注册成功，请等待租户管理员邀请"
}
```

**注册后状态**：

| 状态 | 说明 | 能否登录 | 能否使用业务 |
|-----|------|---------|-------------|
| `pending` | 待邀请 | ✓ | ✗ |
| `active` | 已激活 | ✓ | ✓ |

**完整流程**：

```
1. 用户注册 → pending 状态
2. 租户管理员邀请 → 用户确认
3. 用户确认 → active 状态，成为租户成员
4. 租户管理员分配角色 → 用户获得业务权限
```

#### 10.3.1 平台管理员直接创建账号

除了用户自主注册外，**平台管理员也可以直接创建 User 账号**：

```json
// POST /api/access/users/ (平台管理员调用)
{
  "username": "admin001",
  "password": "xxx",
  "name": "管理员",
  "phone": "13800138000"
}
```

用于内部管理场景（如为客户批量创建账号）。

#### 10.3.2 未来支持手机号注册

未来计划支持手机号注册：

```json
// POST /api/access/users/register/by-phone/
{
  "phone": "13800138000",
  "sms_code": "123456"
}
```

## 12. 认证入口设计

### 12.1 登录响应增加租户列表

登录成功后，返回该用户所属的所有租户：

```json
{
  "business_code": "SUCCESS",
  "username": "zhangsan",
  "tenants": [
    {
      "tenant_id": 1,
      "tenant_code": "tenant_a",
      "tenant_name": "租户A",
      "roles": ["tenant_admin"]
    },
    {
      "tenant_id": 2,
      "tenant_code": "tenant_b",
      "tenant_name": "租户B",
      "roles": ["pilot_operator", "route_planner"]
    }
  ],
  "default_tenant": 1
}
```

### 12.2 租户上下文传递

**使用 HTTP Header 传递租户上下文**：

```
X-Tenant-Code: tenant_a
```

### 12.3 中间件实现

```python
class TenantContextMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        tenant_code = request.headers.get('X-Tenant-Code')

        if tenant_code:
            tenant = Tenant.objects.filter(code=tenant_code, status=1).first()
            if not tenant:
                raise PermissionDenied("Invalid tenant")
            request.tenant_context = tenant
        else:
            request.tenant_context = None  # 平台接口

        return self.get_response(request)
```

### 12.4 View 层使用

```python
class DroneViewSet(...):
    def get_queryset(self):
        tenant = getattr(self.request, 'tenant_context', None)
        if tenant:
            return super().get_queryset().filter(tenant_id=tenant.id)
        # 无租户上下文 = 平台接口（如租户管理）
        return super().get_queryset()
```

## 13. 租户守卫机制

### 13.1 为什么需要

开发者可能会忘记在新建数据时传入 `tenant_id`，导致数据"无主"或跨租户污染。

### 13.2 TenantGuardMixin 实现

使用显式约束，确保数据必须有 tenant_id：

```python
class TenantGuardMixin:
    """租户守卫：确保所有业务数据必须归属某个租户"""

    tenant = models.ForeignKey('access.Tenant', on_delete=models.PROTECT)

    def save(self, *args, **kwargs):
        if not self.tenant_id:
            raise ValidationError("tenant_id is required")
        super().save(*args, **kwargs)

    def clean(self, *args, **kwargs):
        if not self.tenant_id:
            raise ValidationError("tenant_id is required")
        super().clean(*args, **kwargs)
```

**使用示例**：

```python
class Drone(TenantGuardMixin, models.Model):
    code = models.CharField(max_length=64)
    name = models.CharField(max_length=128)
    # ... 其他字段
```

需要保留的部分：

- 现有权限码目录
- `Group` 能力组思想
- `GroupPermissionScope`
- `ALL / OWN / ASSIGNED`
- 业务 View 到权限码的映射方式

需要重构的部分：

- `StaffProfile`：保留，作为用户个人档案（不参与租户逻辑）
- `StaffType`：改为平台固定角色目录 `SystemRole`
- `StaffTypeGroup`：改为固定角色到能力组的绑定
- 授权服务：改为基于 `TenantMember`
- 所有业务模型：补足 `tenant_id`
- 所有业务查询：默认租户过滤
- 所有业务写入：强制同租户校验

---

## 15. 实施顺序

建议按以下顺序推进：

1. 引入 `Tenant`
2. 重构成员模型为 `TenantMember`
3. 固化平台固定角色模型，并加入 `tenant_admin`
4. 所有业务表补 `tenant_id`
5. 重写授权链为"当前租户内授权"
6. 拆分平台管理面与租户管理面
7. 增加数据库级租户隔离

---

## 16. 最终结论

本系统的最终多租户形态应为：

- 平台固定角色
- 租户内成员分配角色
- `tenant_admin` 负责租户治理
- 平台默认不可见租户业务数据
- 所有业务数据显式归属租户
- 所有权限先过租户边界，再做角色与 scope 判定

一句话总结：

本系统应从“单组织权限系统”升级为“平台管租户、租户管成员、业务数据强隔离”的 SaaS 多租户系统。
