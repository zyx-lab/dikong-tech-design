# 角色权限重构文档

日期：2026-03-13
版本：v1.22

## 1. 文档定位

这份文档记录的是下一阶段权限模型重构的目标态，不等同于当前代码现状。

当前代码已经完成了第一轮多租户权限收口，运行时大致是：

- `TenantMember -> TenantMemberRole -> SystemRole -> SystemRoleGroup -> GroupPermissionScope`
- `TenantMemberPosition` 和 `TenantMemberQualification` 已存在
- `StaffType` 已从运行时主链移除

在继续讨论后，目标模型进一步收敛为：

- 不再保留 `SystemRole / Group / TenantMemberPosition`
- `Role` 收敛为平台级角色目录
- `Role` 统一承载“岗位 + 管理职责”
- 角色与权限映射由平台统一定义，租户管理员不可修改
- `TenantMember` 只保存租户内关系字段，不重复保存 `StaffProfile` 已有字段
- 邀请只面向已存在的 `User`
- `TenantMemberQualification` 升级为“资质类型 + 成员资质记录”两层模型
- 用代码内固定状态机固化成员状态迁移

后续代码重构应以本文档为准。

## 2. 本次定稿结论

### 2.1 平台固定目录和租户运行数据分离

本轮明确分成两类表：

平台固定目录表：

- `Role`
- `Permission`
- `RolePermissionGrant`
- `QualificationType`

租户运行数据表：

- `Tenant`
- `TenantMember`
- `TenantMemberRole`
- `TenantMemberQualification`

怎么理解这组划分：

- 平台固定目录表，保存的是“平台统一定义的标准答案”
- 租户运行数据表，保存的是“某个租户实际在运行中的业务数据”

可以直接这样理解：

- `Role`：平台先定义有哪些角色，例如 `pilot / tenant_admin`
- `Permission`：平台先定义有哪些权限，例如 `mission.view / mission.execute`
- `RolePermissionGrant`：平台先定义“某个角色默认拥有哪些权限”
- `QualificationType`：平台先定义有哪些资质类型，例如 `pilot_license`

上面这些都不属于某一个租户，而是所有租户共用的基础规则。

而下面这些，是某个租户自己实际产生的数据：

- `Tenant`：这个租户本身
- `TenantMember`：某个用户加入了这个租户
- `TenantMemberRole`：这个租户里的这个成员，被授了哪些平台角色
- `TenantMemberQualification`：这个租户里的这个成员，录入了哪些资质记录

一句话说：

- 平台固定目录表 = 平台定义规则
- 租户运行数据表 = 租户实际使用这些规则后的结果

示例：

- 平台先定义 `Role=pilot`
- 平台先定义 `Permission=mission.execute`
- 平台先定义 `pilot -> mission.execute`
- 这些都属于平台固定目录
- 某个租户里张三加入成为成员、被授予 `pilot`、再录入飞手执照
- 这些都属于租户运行数据

设计原则：

- 平台固定目录由平台迁移统一维护
- 租户管理员不可修改平台固定目录
- 租户运行数据只保存“谁在这个租户里、被授予了什么角色、具备什么资质”
- `OWN / ASSIGNED` 只用于平台代码里已经明确支持细粒度判定的少量资源

### 2.2 `Role` 是平台级统一角色层

本轮的准确表述不是“角色等于岗位表”，而是：

- `Role` 是平台级统一角色层
- 这层同时承载“岗位角色”和“管理职责角色”

例如：

- `pilot`
- `dispatcher`
- `maintenance`
- `tenant_admin`

其中：

- `pilot`、`dispatcher` 更偏业务岗位
- `tenant_admin` 更偏管理职责

它们都统一落在平台级 `Role` 目录里，不再按租户复制一份。

### 2.3 授权链和业务校验链分开

授权链只解决“能不能做”：

```text
User(ACTIVE) + Tenant(ACTIVE) -> TenantMember(ACTIVE) -> TenantMemberRole(GRANTED) -> Role(ACTIVE) -> RolePermissionGrant -> Permission(ACTIVE)
```

业务校验链只解决“业务上是否满足执行条件”：

```text
User(ACTIVE) + Tenant(ACTIVE) -> TenantMember(ACTIVE) -> TenantMemberQualification(有效记录) -> QualificationType(ACTIVE)
```

业务判断规则固定为：

- 授权链和业务校验链都必须先满足 `User.status = ACTIVE` 且 `Tenant.status = ACTIVE`
- 岗位/职责类业务判断，认平台内置 `role.code`
- 系统授权判断，认 `Permission`
- 执行资格类业务判断，认“内置 `role.code` + 有效资质记录”
- 不允许通过权限集合反推业务身份

### 2.4 `TenantMember` 只保存租户内关系字段

`TenantMember` 只表达“某个用户在某个租户中的成员关系”。

明确约束：

- 不在 `TenantMember` 再存 `name`
- 不在 `TenantMember` 再存 `phone`
- 不在 `TenantMember` 再存 `email`

这些信息统一以 `StaffProfile` 为准。

`TenantMember` 只保留租户内字段，例如：

- `member_no`
- `display_name`
- `status`
- 邀请状态相关字段
- 加入时间

其中：

- `display_name` 是租户内显示别名，可为空
- 如果为空，界面回退展示 `StaffProfile.name`

### 2.5 邀请只面向已存在账号

本轮约束明确为：

- 没创建的 `User` 不能被邀请
- 租户邀请只面向平台中已存在的 `User`
- 邀请动作创建的是一条待激活的 `TenantMember` 关系

因此邀请模型的正确表达是：

- `User` 先存在
- `TenantMember.user_id` 在邀请时就已确定
- `TenantMember.status=INVITED`
- 接受邀请时只激活成员关系，不再新建或补绑 `User`

如果未来要支持“手机号/邮箱直邀未注册用户”，那应另开注册引导链路，不混入本版模型。

### 2.6 邀请历史不单独建表

本轮不为邀请过程单独保留历史表。

设计原则：

- 邀请状态只保留当前状态
- 拒绝、过期、撤销都直接更新当前这条 `TenantMember`
- 重发邀请时复用同一条 `TenantMember`
- `INVITED / REJECTED / EXPIRED / REVOKED` 可保留“当前这次邀请”的元数据
- `ACTIVE / DISABLED` 不再保留邀请元数据

这意味着：

- 不新增 `InvitationHistory`
- 不新增“邀请多版本记录表”
- 一条成员关系记录只表达当前状态

### 2.7 `TenantMemberRole` 的合法状态集合和判定口径

本轮不再让 `TenantMemberRole` 使用容易歧义的 `ACTIVE / DISABLED` 语义。

合法状态集合只保留：

- `GRANTED`
- `REVOKED`

判定口径：

- `GRANTED` 表示“绑定关系有效”
- `REVOKED` 表示“绑定关系已撤销”
- `GRANTED` 不等于“当前一定生效”

角色绑定真正贡献权限的条件固定为：

```text
User.status = ACTIVE
且 Tenant.status = ACTIVE
且 TenantMember.status = ACTIVE
且 TenantMemberRole.status = GRANTED
且 Role.status = ACTIVE
且存在对应的 RolePermissionGrant
且 Permission.status = ACTIVE
```

因此：

- 邀请态可以预绑定角色，并将状态写为 `GRANTED`
- 但只要成员不是 `ACTIVE`，这些角色绑定都不参与授权

### 2.8 `member_no` 不是激活门槛，但受状态约束

本轮明确：

- 成员一旦 `ACTIVE`，就表示已经是正式成员
- `member_no` 可以在激活后再分配
- 因此 `member_no` 不是 `ACTIVE` 的前置门槛
- `member_no` 一旦分配，默认视为租户内不可复用编号

具体约束：

- `ACTIVE` 状态下，`member_no` 可为空
- 只有 `ACTIVE` 成员允许分配或修改 `member_no`
- `INVITED / REJECTED / EXPIRED / REVOKED` 状态下，`member_no` 必须为空
- `DISABLED` 状态下，已分配的 `member_no` 可以保留
- `DISABLED` 状态下保留的 `member_no` 继续占用唯一性，不允许分配给其他成员
- 本版不提供“释放并复用工号”的流程；如未来要支持，需单独设计释放规则

### 2.9 资质关键字段缺失即无效

本轮把“缺失关键字段，应视为无效”写成硬规则。

对需要有效期的资质类型：

- `valid_from` 必填
- `valid_until` 必填
- `valid_from <= valid_until`

缺失任一关键字段，都视为无效记录，不参与业务校验。

同时：

- `QualificationType` 由平台统一定义
- 平台可在 `payload_schema_json` 中声明该资质类型的必填扩展字段
- `payload_json` 缺失必填字段时，同样视为无效记录
- `QualificationType.status = DISABLED` 时，该类型下所有资质记录都不再参与业务校验
- 本版不支持“禁止新写入但保留存量继续有效”的中间状态

### 2.10 `scope_type` 只保留 3 种

本版不保留 `DEPT`。

首版 `scope_type` 只保留：

- `ALL`
- `ASSIGNED`
- `OWN`

并明确合并规则：

- 多角色命中同一权限时，取更高权限范围
- 只对满足授权前置条件的映射参与范围合并
- 优先级固定为：`ALL > ASSIGNED > OWN`

其中“满足授权前置条件”固定指：

```text
User.status = ACTIVE
且 Tenant.status = ACTIVE
且 TenantMember.status = ACTIVE
且 TenantMemberRole.status = GRANTED
且 Role.status = ACTIVE
且存在对应的 RolePermissionGrant
且 Permission.status = ACTIVE
```

范围判定口径固定为：

- `ALL`：不做资源归属限制
- `OWN`：当前 `tenant_member_id` 必须命中该 `resource_code` 在代码中定义的 owner 判定
- `ASSIGNED`：当前 `tenant_member_id` 必须命中该 `resource_code` 在代码中定义的 assignment 判定
- `OWN / ASSIGNED` 一律以当前租户内的 `tenant_member_id` 为判定主体，不使用 `user_id` 直接判定
- 只有需要细粒度资源判定的 `Permission` 才需要绑定 `resource_code`
- `OWN / ASSIGNED` 只允许用于平台代码里已经实现资源归属判定的 `resource_code`
- 若资源当前没有 assignment，`ASSIGNED` 就不对任何成员放行
- 不需要细粒度资源判定的权限，统一只使用 `ALL`

### 2.11 平台固定目录状态统一口径

本轮把平台固定目录的 `status` 语义统一收敛。

适用表：

- `Role`
- `Permission`
- `QualificationType`

合法状态集合统一为：

- `ACTIVE`
- `DISABLED`

判定口径：

- `ACTIVE` 表示该目录项可参与运行时判定
- `DISABLED` 表示该目录项已停用，但记录保留，用于升级、修复和对账
- 运行时只认 `ACTIVE` 的平台目录项
- `ACTIVE / DISABLED` 可双向切换
- 当前阶段不实现自动升级脚本
- 如需停用或回启，由平台管理员手工修改
- 目录项重新启用后，历史上仍满足当前规则的数据会重新参与运行时判定
- 若不希望历史数据重新生效，由平台管理员或租户管理员手工修正相关角色绑定、权限映射、资源归属 / 分配或资质记录

## 3. 最终结构总览

```text
User
 └─1:1─ StaffProfile

Tenant
 └─1:N─ TenantMember
          ├─1:N─ TenantMemberRole ── N:1 ── Role
          └─1:N─ TenantMemberQualification ── N:1 ── QualificationType

Role
 └─1:N─ RolePermissionGrant ── N:1 ── Permission
```

怎么理解这张图：

- `User └─1:1─ StaffProfile`
- 一个登录账号 `User` 对应一份全局人员档案 `StaffProfile`
- `User` 管登录、认证、账号状态
- `StaffProfile` 管这个人是谁，例如姓名、手机号、邮箱

- `Tenant └─1:N─ TenantMember`
- 一个租户可以有很多成员
- `TenantMember` 不是用户本身，而是“某个用户在某个租户中的成员关系”

- `TenantMember ├─1:N─ TenantMemberRole ── N:1 ── Role`
- 一个成员可以绑定多个角色
- `TenantMemberRole` 是绑定记录，表示“这个成员被授了哪个平台角色”
- `Role` 是平台统一定义的角色，例如 `pilot / tenant_admin`

- `TenantMember └─1:N─ TenantMemberQualification ── N:1 ── QualificationType`
- 一个成员可以有多条资质记录
- `TenantMemberQualification` 是成员实际录入的资质数据
- `QualificationType` 是平台统一定义的资质类型，例如 `pilot_license`

- `Role └─1:N─ RolePermissionGrant ── N:1 ── Permission`
- 一个角色可以关联多条权限映射
- `RolePermissionGrant` 表示“这个角色拥有哪些权限”
- `Permission` 表示系统中定义好的某项能力，例如 `mission.execute`

一句话理解整张图：

- `User / StaffProfile` 解决“这个人是谁”
- `TenantMember` 解决“这个人在哪个租户里”
- `TenantMemberRole` 解决“这个人在这个租户里是什么角色”
- `RolePermissionGrant` 解决“这个角色能做什么”
- `TenantMemberQualification` 解决“这个人在业务上具备什么资质”

把这张图翻成一个具体例子：

- 平台里先有一个账号 `User(zhangsan)`
- 这个账号有一份档案 `StaffProfile(name=张三)`
- 平台里先定义好 `Role=pilot`
- 平台里先定义好 `Permission=mission.execute`
- 平台里先定义好 `pilot -> mission.execute`

然后某个租户 `acme` 里：

- 张三加入 `acme`，形成一条 `TenantMember`
- 张三在 `acme` 里被授予 `pilot`，形成一条 `TenantMemberRole`
- 如果张三录入了飞手执照，就形成一条 `TenantMemberQualification`

于是：

- 从成员关系上看，张三是 `acme` 的成员
- 从角色上看，张三在 `acme` 里是 `pilot`
- 从授权上看，张三因为拥有 `pilot`，继承了 `mission.execute`
- 从业务资格上看，张三是否真的允许执行飞行，还要再看 `pilot_license` 是否有效

授权主链：

```text
User(ACTIVE) + Tenant(ACTIVE) -> TenantMember(ACTIVE) -> TenantMemberRole(GRANTED) -> Role(ACTIVE) -> RolePermissionGrant -> Permission(ACTIVE)
```

业务校验链：

```text
User(ACTIVE) + Tenant(ACTIVE) -> TenantMember(ACTIVE) -> TenantMemberQualification(有效记录) -> QualificationType(ACTIVE)
```

注意：

- `INVITED` 成员可以预绑定角色
- 但 `INVITED / REJECTED / EXPIRED / REVOKED / DISABLED` 成员都不进入授权链
- `Tenant.status = ACTIVE` 是两条链的共同前置门禁

## 4. 最终表字段草图

### 4.1 `User`

职责：

- 只表示“谁能登录系统”
- 不保存租户身份
- 不保存租户工号
- 不保存角色

建议字段：

```text
id
username
password_hash
status
is_superuser
last_login_at
created_at
updated_at
```

合法状态集合：

```text
ACTIVE
DISABLED
```

说明：

- 只有 `ACTIVE` 的 `User` 可登录并参与租户内授权链和业务校验链
- `DISABLED` 的 `User` 不参与任何租户内授权和业务判定
- `is_superuser=true` 只表示平台级超级管理员身份
- `is_superuser=true` 可进入平台级管理接口，不依赖 `TenantMember`
- `is_superuser=true` 不直接替代租户成员身份，不直接推导 `role.code`
- 对租户内业务操作，若接口依赖 `TenantMember / role.code / 资质`，则 `is_superuser=true` 也必须走显式租户上下文或专用平台运维接口

### 4.2 `StaffProfile`

职责：

- 全局人员档案
- 只保存“这个人是谁”
- 作为展示名、手机号、邮箱等基础信息来源

建议字段：

```text
id
user_id unique
name
phone
email
id_card_no nullable
gender nullable
avatar_url nullable
created_at
updated_at
```

说明：

- `StaffProfile` 只保存全局人员基础信息
- 不保存租户内成员关系状态
- 不保存租户内在职/离职口径
- 不与 `TenantMember.status` 形成双写或双真相

### 4.3 `Tenant`

职责：

- 表示一个租户/客户空间

建议字段：

```text
id
code unique
name
status
plan_code nullable
remark nullable
created_at
updated_at
```

合法状态集合：

```text
ACTIVE
DISABLED
```

说明：

- 只有 `ACTIVE` 的 `Tenant` 允许执行租户内授权和业务校验
- `DISABLED` 的 `Tenant` 下，成员关系和角色绑定可保留，但不参与运行时判定
- `plan_code` 不属于授权链字段，不直接决定 `Role / Permission / QualificationType`
- 在额度/权益模型单独落地前，`plan_code` 只作为套餐标识，不得被业务代码直接当作授权条件

### 4.4 `Role`

职责：

- 平台级统一角色目录
- 同时承载岗位角色与管理职责角色

建议字段：

```text
id
code unique
name
description nullable
status
created_at
updated_at
```

说明：

- `Role` 不再挂 `tenant_id`
- 所有租户共享同一套角色目录
- 平台迁移统一维护 `Role`
- 租户管理员不可新增、删除或修改 `Role`
- `code` 是发布后的稳定编码，创建后不得修改
- `status` 只允许 `ACTIVE / DISABLED`

示例：

```text
code=pilot
name=飞手
status=ACTIVE
```

```text
code=tenant_admin
name=租户管理员
status=ACTIVE
```

### 4.5 `Permission`

职责：

- 定义系统中有哪些可授权能力

建议字段：

```text
id
code unique
name
module
resource_code nullable
description nullable
status
created_at
updated_at
```

合法状态集合：

```text
ACTIVE
DISABLED
```

说明：

- `Permission` 是平台固定目录
- 只有 `ACTIVE` 的 `Permission` 可参与授权计算
- 只在 `OWN / ASSIGNED` 场景下要求 `resource_code` 非空
- 只使用 `ALL` 的权限，`resource_code` 可为空
- `Permission.code` 是发布后的稳定编码，创建后不得修改
- `resource_code` 会直接影响授权语义，不放进通用自动升级脚本
- 若确需调整 `resource_code`，由平台管理员手工修改，并立即重跑一致性检查；必要时先将相关 `Permission` 置为 `DISABLED`

示例编码：

```text
mission.view
mission.create
mission.assign_pilot
mission.execute
drone.view
drone.bind_device
member.manage
role.manage
```

### 4.6 `RolePermissionGrant`

职责：

- 表示某个角色拥有哪些权限
- 这是平台固定授权目录，不是租户自定义授权记录

建议字段：

```text
id
role_id
permission_id
scope_type
created_at
updated_at
```

建议约束：

```text
unique(role_id, permission_id)
check(scope_type in (ALL, ASSIGNED, OWN))
```

`scope_type` 只保留：

```text
ALL
ASSIGNED
OWN
```

说明：

- 本表由平台迁移统一维护
- 租户管理员不可修改
- 多角色命中同一权限时，按 `ALL > ASSIGNED > OWN` 合并
- 本表不再单独保留 `status`
- 映射记录存在，就表示该角色当前拥有该权限
- 若平台要撤销该映射，直接删除该记录
- 运行时只对 `Role.status = ACTIVE` 且 `Permission.status = ACTIVE` 的映射参与计算
- `OWN / ASSIGNED` 一律使用当前租户上下文中的 `TenantMember.id` 作为判定主体
- `OWN / ASSIGNED` 只能用于 `Permission.resource_code` 非空，且该 `resource_code` 已在平台代码中实现资源归属判定的权限
- 当前资源无 assignment 时，`ASSIGNED` 判定结果为“不命中任何成员”，而不是脏数据
- `scope_type` 会直接影响授权范围，不放进通用自动升级脚本
- 若确需调整 `scope_type`，由平台管理员手工修改，并立即重跑一致性检查；必要时先停用相关 `Role` 或 `Permission`
- 资源接入 `OWN / ASSIGNED` 前，必须先完成字段落库、历史数据回填和一致性检查，不允许先切权限范围再补数据

### 4.7 `QualificationType`

职责：

- 定义资质类型
- 解决“有哪些资质种类”

建议字段：

```text
id
code unique
name
description nullable
requires_validity
payload_schema_json nullable
status
created_at
updated_at
```

说明：

- `QualificationType` 由平台统一定义
- 租户侧不可自定义
- `payload_schema_json` 可声明扩展字段及必填项
- `status` 只允许 `ACTIVE / DISABLED`
- `ACTIVE` 表示该资质类型可写入、可参与业务校验
- `DISABLED` 表示平台当前版本已不再认可该资质类型，存量记录仅保留展示、升级和修复价值，不再参与业务校验
- 本版不额外引入“仅禁止新写入但保留存量继续有效”的中间状态
- `QualificationType.code` 是发布后的稳定编码，创建后不得修改
- `payload_schema_json` 会直接影响业务校验口径，不放进通用自动升级脚本
- 若确需调整 `payload_schema_json`，由平台管理员手工修改定义；租户管理员补齐、修正或作废成员资质记录；修不回来的记录统一标记为 `INVALID`

示例：

```text
code=pilot_license
name=飞手执照
requires_validity=true
status=ACTIVE
```

### 4.8 成员状态迁移规则

职责：

- 固化 `TenantMember.status` 的合法迁移矩阵
- 服务层只能执行本文第 6 章允许的迁移

实现方式：

- 本版不单独建 `TenantMemberStatusTransitionRule` 表
- 状态迁移矩阵直接固化在服务代码中
- 若后续要调整迁移规则，直接随平台代码版本一起升级

### 4.9 `TenantMember`

职责：

- 表示某个用户在某个租户中的成员关系
- 同时承载邀请生命周期的当前状态

建议字段：

```text
id
tenant_id
user_id
member_no nullable
display_name nullable
status
invitation_token nullable
invited_by_user_id nullable
invited_at nullable
expires_at nullable
responded_at nullable
joined_at nullable
created_at
updated_at
```

建议约束：

```text
unique(tenant_id, user_id)
unique(tenant_id, member_no)          # member_no 非空时生效
unique(invitation_token)              # token 非空时生效
```

状态集合：

```text
INVITED
ACTIVE
REJECTED
EXPIRED
REVOKED
DISABLED
```

说明：

- 不保存 `StaffProfile` 已有字段，例如 `name/phone/email`
- `display_name` 是租户内显示别名，可为空
- `member_no` 是租户内编号
- 一条记录只表示当前状态，不保留邀请历史版本
- `INVITED / REJECTED / EXPIRED / REVOKED` 可保留当前这次邀请的元数据
- `ACTIVE / DISABLED` 必须清空邀请元数据
- `ACTIVE` 状态下，`member_no` 可为空
- 只有 `ACTIVE` 成员允许分配或修改 `member_no`
- `INVITED / REJECTED / EXPIRED / REVOKED` 状态下，`member_no` 必须为空
- `DISABLED` 状态下，已分配的 `member_no` 可以保留
- `DISABLED` 状态下保留的 `member_no` 继续占用唯一性，不允许其他成员复用
- 本版不提供“释放并复用工号”的流程

状态字段约束矩阵：

```text
INVITED:
- invitation_token / invited_by_user_id / invited_at / expires_at 必填
- responded_at / joined_at / member_no 必须为空

ACTIVE:
- responded_at / joined_at 必填
- invitation_token / invited_by_user_id / invited_at / expires_at 必须为空
- member_no 可为空

REJECTED:
- invited_by_user_id / invited_at / expires_at 必填
- responded_at 必填
- invitation_token 必须为空
- joined_at / member_no 必须为空

EXPIRED:
- invited_by_user_id / invited_at / expires_at 必填
- invitation_token 必须为空
- responded_at / joined_at / member_no 必须为空

REVOKED:
- invited_by_user_id / invited_at / expires_at 必填
- invitation_token 必须为空
- responded_at / joined_at / member_no 必须为空

DISABLED:
- responded_at / joined_at 必须保留
- invitation_token / invited_by_user_id / invited_at / expires_at 必须为空
- member_no 可保留
```

邀请态示例：

```text
tenant_id=10
user_id=101
display_name=张三（华东租户）
status=INVITED
invitation_token=inv_abc123
invited_by_user_id=9001
invited_at=2026-03-13 14:00:00
expires_at=2026-03-20 23:59:59
```

### 4.10 `TenantMemberRole`

职责：

- 表示成员被授予了哪些平台角色

建议字段：

```text
id
tenant_member_id
role_id
status
assigned_by_user_id nullable
assigned_at
created_at
updated_at
```

建议约束：

```text
unique(tenant_member_id, role_id)
fk (tenant_member_id) -> TenantMember(id)
fk (role_id) -> Role(id)
```

合法状态集合：

```text
GRANTED
REVOKED
```

判定口径：

- `GRANTED` 表示绑定记录有效
- `REVOKED` 表示绑定记录已撤销
- 是否真正贡献权限，必须同时满足 `User.status / Tenant.status / TenantMember.status / Role.status / RolePermissionGrant / Permission.status` 的完整授权条件

说明：

- `Role` 是平台级角色，不存在“角色属于某个租户”的问题
- 租户边界由 `TenantMember` 承担
- 创建或恢复 `TenantMemberRole.status=GRANTED` 时，`Role.status` 必须为 `ACTIVE`
- 成员非 `ACTIVE` 时，已有 `GRANTED` 绑定记录可以保留，但不生效
- 同一 `(tenant_member_id, role_id)` 在全生命周期只保留一条记录
- 若已存在 `REVOKED` 记录，重新授予时必须原地更新为 `GRANTED`，并刷新 `assigned_by_user_id / assigned_at / updated_at`
- 若已存在 `GRANTED` 记录，再次授予视为幂等成功，不新增第二条记录
- 若某个 `Role` 后续被平台置为 `DISABLED`，历史绑定记录可以保留，但不得继续新授予或从 `REVOKED` 恢复为 `GRANTED`

示例：

```text
tenant_member_id=501
role_id=1001        # code=pilot
status=GRANTED
assigned_at=2026-03-13 10:00:00
```

### 4.11 `TenantMemberQualification`

职责：

- 保存成员持有的具体资质记录
- 只用于业务校验，不进入授权链

建议字段：

```text
id
tenant_member_id
qualification_type_id
certificate_no nullable
level nullable
status
issued_at nullable
valid_from nullable
valid_until nullable
issuer nullable
payload_json nullable
created_at
updated_at
```

建议索引：

```text
index(tenant_member_id, qualification_type_id)
index(tenant_member_id, status)
```

合法状态集合：

```text
ACTIVE
INVALID
REVOKED
```

说明：

- 不再使用 `unique(tenant_member_id, code)`
- 同一成员允许拥有同一资质类型的多条记录
- 用于支持续证、多证并存和扩展字段
- 业务判定时，按“是否存在至少一条有效记录”来判断是否具备该资质
- 写入时必须先根据 `qualification_type_id` 加载 `QualificationType`，再执行服务层校验
- `ACTIVE` 表示记录结构合法，可继续参与有效性计算
- `INVALID` 表示记录字段缺失、日期非法或 payload 不满足 schema，不参与业务判定
- `REVOKED` 表示记录已被业务吊销、撤销或作废，不参与业务判定
- 不单独落 `EXPIRED` 状态，是否过期由 `valid_from / valid_until` 实时计算

有效记录定义：

```text
User.status = ACTIVE
且 Tenant.status = ACTIVE
且 TenantMember.status = ACTIVE
且 QualificationType.status = ACTIVE
且 TenantMemberQualification.status = ACTIVE
且 (
  QualificationType.requires_validity = false
  或 (
    valid_from is not null
    且 valid_until is not null
    且 valid_from <= today
    且 valid_until >= today
    且 valid_from <= valid_until
  )
)
且 payload_json 满足 QualificationType.payload_schema_json 的必填约束
```

缺失关键字段时的处理：

- 对 `requires_validity=true` 的资质，`valid_from` 或 `valid_until` 为空，直接视为无效
- `payload_schema_json` 声明的必填字段缺失，直接视为无效
- 正常写入路径遇到这类数据时必须拒绝写入
- 历史已存在脏数据时，统一修复为 `INVALID`
- 若修改 `payload_schema_json` 后历史记录不再满足当前规则，应由平台管理员和租户管理员修复或标记为 `INVALID`，不做自动兼容

写入校验规则：

```text
1. 先加载 QualificationType
2. 若 QualificationType.requires_validity = true：
   - valid_from 必填
   - valid_until 必填
   - valid_from <= valid_until
3. 按 QualificationType.payload_schema_json 校验 payload_json 必填字段
4. 校验失败时拒绝写入，不允许落脏数据
```

数据库与修复约束：

```text
- 数据库至少增加 check(valid_from <= valid_until) when both not null
- 对历史脏数据，运行修复脚本扫描并标记为 INVALID
- 正常业务接口不应直接写入 INVALID，INVALID 只用于修复和巡检标记
```

示例：

```text
tenant_member_id=501
qualification_type_id=2001   # code=pilot_license
certificate_no=CAAC-778899
level=IV
status=ACTIVE
issued_at=2025-01-01
valid_from=2025-01-01
valid_until=2027-12-31
payload_json={"aircraft_class":"multi_rotor"}
```

## 5. 术语说明与平台目录升级机制

### 5.1 什么是自然键

自然键指的是“业务上本来就稳定、可唯一标识一条记录的字段或字段组合”，而不是数据库自动生成的自增 `id`。

在本模型中：

```text
Role: code
Permission: code
QualificationType: code
RolePermissionGrant: (role_code, permission_code)
```

这些自然键的作用是：

- 不同环境中的数据库 `id` 可能不同
- 但业务编码应保持稳定
- 平台升级或补齐目录时，应按自然键判断“是不是同一条业务记录”
- `Role.code / Permission.code / QualificationType.code` 一经发布，不再修改

因此：

- `id` 用于数据库内部关联
- 自然键用于版本升级、补齐和对账

### 5.2 这里说的“升级”是什么意思

这里的“升级”不是指成员状态变化，也不是指用户升级账号。

这里指的是：

- 平台代码版本升级
- 数据模型版本升级
- 平台固定目录版本升级

也就是平台发新版本时，需要把新版本中定义的固定角色、固定权限、资质类型，同步到数据库中。

例如：

1. 新增一个平台角色  
   例如新增 `auditor`
2. 给已有角色补权限  
   例如给 `tenant_admin` 增加 `member.export`
3. 废弃一个资质类型  
   例如停用某个旧证照类型
4. 调整成员状态机  
   例如增加新的成员恢复流程

所以这里的“升级”，本质上就是：

- 平台新版本的标准答案变了
- 数据库里的固定目录也要同步到这个新标准答案

### 5.3 这里说的“修复”是什么意思

这里的“修复”不是新增业务能力，而是把已有脏数据、缺失数据、过期数据修回到当前标准。

例如：

- 平台目录缺少某个固定角色
- `TenantMember.status` 和字段值不一致
- `TenantMemberRole` 存在孤儿引用
- 资质记录缺少关键字段

所以这里的“修复”，本质上就是：

- 当前数据已经偏离目标模型
- 需要用修复脚本和一致性检查把它拉回标准状态

### 5.4 现阶段平台目录维护原则

当前阶段先不做自动升级脚本，也不做自动补齐系统。

平台目录和异常数据统一按“人工维护 + 最小检查 + 管理员兜底”处理。

统一规则：

1. `Role / Permission / RolePermissionGrant / QualificationType` 由平台维护
2. 目录项新增、停用、回启、字段调整，统一由平台管理员手工修改
3. 租户运行数据异常，统一由租户管理员手工修正
4. 会直接改变运行时结果的内容，一律不自动处理：
   - `Role.status / Permission.status / QualificationType.status`
   - `Permission.resource_code`
   - `RolePermissionGrant.scope_type`
   - `QualificationType.payload_schema_json`
   - 给已有 `Role` 新增 `RolePermissionGrant`
5. 带 `status` 的平台固定目录表只允许 `ACTIVE / DISABLED`
6. 现阶段不做复杂自动兼容，不做自动放权，不做自动推断

自然键定义：

```text
Role: code
Permission: code
QualificationType: code
RolePermissionGrant: (role_code, permission_code)
```

#### 5.4.1 旧数据迁移原则

从旧模型迁到本模型时：

1. 先创建平台级 `Role` 目录
2. 创建平台级 `Permission` 目录
3. 用旧的 `SystemRole.code` 映射到新的 `Role.code`
4. 将旧成员角色绑定回填到 `TenantMemberRole`
5. 若旧数据里同一成员对同一角色存在多条绑定，必须收敛为一条
6. 将旧权限链统一回填到平台级 `RolePermissionGrant`
7. 若某权限将使用 `OWN / ASSIGNED`，必须先在代码里补齐该 `resource_code` 的 owner / assignment 判定，并完成历史数据回填
8. 未能匹配的旧 `code` 或 `resource_code`，直接记为待人工处理项，不自动推断，也不自动放大权限；由平台管理员补目录、租户管理员补运行数据
9. 成员状态迁移规则不做表迁移，直接按本文第 6 章落到代码中

目录回填顺序：

```text
1. Role
2. Permission
3. RolePermissionGrant
4. QualificationType
```

#### 5.4.1.A `OWN / ASSIGNED` 资源接入规则

任何资源想接入 `OWN / ASSIGNED` 权限范围，至少要满足：

1. 先在 `Permission` 中为该权限绑定非空 `resource_code`
2. 再在平台代码中实现该 `resource_code` 的 owner / assignment 判定
3. 相关资源数据必须已经完成必要回填
4. 若任一条件不满足，不自动回退到 `ALL`；由平台管理员手工调整 `Permission / RolePermissionGrant`，租户管理员修资源数据

简单执行原则：

- 没补完代码判定和资源数据前，不要启用 `OWN / ASSIGNED`
- 首版只支持少量写死在代码里的 `resource_code`

#### 5.4.2 上线后的维护规则

后续版本新增角色、权限、资质类型，或调整成员状态机时：

1. 先由平台管理员手工维护目录项
2. 再运行最小一致性检查
3. 最小一致性检查至少覆盖：
   - 平台固定角色、权限、资质类型存在
   - 使用 `OWN / ASSIGNED` 的权限，其 `Permission.resource_code` 非空
   - `RolePermissionGrant` 不存在孤儿引用，且 `scope_type` 只出现 `ALL / ASSIGNED / OWN`
   - 使用 `OWN / ASSIGNED` 的 `resource_code` 已在代码中实现
   - `TenantMember` 状态与字段矩阵一致
   - `TenantMemberRole` 不存在孤儿引用、重复绑定，且状态只出现 `GRANTED / REVOKED`
   - `TenantMemberQualification` 不存在孤儿引用，且 `ACTIVE` 记录满足关键字段和 schema 约束
4. 一致性检查不通过，就先由管理员修数据，再重跑检查

处理原则：

- 历史 `DISABLED` 目录项如需回启，由平台管理员手工操作
- 回启后，历史上仍满足当前规则的数据会重新生效；若不希望如此，由平台管理员或租户管理员手工修正
- `OWN / ASSIGNED` 所需代码判定或资源数据未就绪时，不自动回退到 `ALL`
- 某资源如果暂时不满足细粒度权限条件，就先不要给它启用 `OWN / ASSIGNED`
- 给已有角色新增权限映射，统一由平台管理员手工执行
- 涉及授权语义或业务校验口径的变化，不做自动处理
- 当前阶段优先人工兜底，不做复杂自动化
- 角色授予接口、邀请预绑定流程和修复脚本，都必须拒绝把 `DISABLED Role` 写成 `TenantMemberRole.status=GRANTED`

这样做的目的，是消除“每个租户一份角色拷贝”的升级漂移问题。

#### 5.4.3 发布后修复方案

如果历史数据已经存在不一致，修复顺序收敛为：

1. 平台管理员修平台目录
   - 按自然键补齐 `Role / Permission / RolePermissionGrant / QualificationType`
   - 需要停用的目录项改为 `DISABLED`
   - 需要恢复的目录项改为 `ACTIVE`
   - 需要调整的 `Permission.resource_code / RolePermissionGrant.scope_type / QualificationType.payload_schema_json` 由平台管理员手工修正
   - 若确需给已有角色新增权限映射，由平台管理员手工新增 `RolePermissionGrant`
   - 对暂时修不好的细粒度权限，可先停用相关 `Role / Permission`，或删除对应 `RolePermissionGrant`，避免继续错误放权
2. 租户管理员修运行数据
   - 修复 `TenantMember.status` 与 `invitation_token / invited_by_user_id / invited_at / expires_at / responded_at / joined_at / member_no` 的不一致
   - 修复资源 owner / assignment 数据
3. 租户管理员修角色绑定
   - 同一 `(tenant_member_id, role_id)` 的多条记录收敛为一条
   - 已撤销角色重新授予时，仅当 `Role.status = ACTIVE` 才允许回写原记录为 `GRANTED`，且不新增第二条
   - 若 `Role.status = DISABLED`，禁止把记录修回 `GRANTED`；历史记录可保留，但必须保持非新增、非恢复状态
   - 将手工移除的绑定统一标记为 `REVOKED`
4. 租户管理员修资质记录
   - 对缺失关键字段、日期非法、payload 缺字段的记录标记为 `INVALID`
   - 对业务上已吊销、撤销、作废的记录标记为 `REVOKED`
   - 不允许继续保留“结构不合法但状态仍是 ACTIVE”的资质记录

修复完成后必须再次跑一致性检查；未通过就继续人工修，不靠自动放宽权限兜底。

## 6. `TenantMember` 状态迁移矩阵

本轮把状态迁移写成平台固定规则。

### 6.1 合法迁移矩阵

| from | to | trigger_code | 说明 |
| --- | --- | --- | --- |
| `INVITED` | `ACTIVE` | `accept_invitation` | 接受邀请 |
| `INVITED` | `REJECTED` | `reject_invitation` | 拒绝邀请 |
| `INVITED` | `EXPIRED` | `expire_invitation` | 到期任务关闭 |
| `INVITED` | `REVOKED` | `revoke_invitation` | 管理员撤销 |
| `INVITED` | `INVITED` | `resend_invitation` | 重发邀请，刷新 token 和时间 |
| `REJECTED` | `INVITED` | `resend_invitation` | 拒绝后重发 |
| `EXPIRED` | `INVITED` | `resend_invitation` | 过期后重发 |
| `REVOKED` | `INVITED` | `resend_invitation` | 撤销后重新发起 |
| `ACTIVE` | `DISABLED` | `disable_member` | 禁用成员 |
| `DISABLED` | `ACTIVE` | `enable_member` | 重新启用成员 |

除上述规则外，其余迁移一律非法。

### 6.2 角色绑定在状态迁移中的处理

成员状态迁移时，`TenantMemberRole` 处理规则固定为：

- `INVITED -> ACTIVE`：已有 `GRANTED` 绑定立即生效
- `INVITED -> REJECTED / EXPIRED / REVOKED`：绑定记录保留，但不生效
- `REJECTED / EXPIRED / REVOKED -> INVITED`：默认沿用原有 `GRANTED` 绑定；如需调整，先显式改绑定
- `ACTIVE -> DISABLED`：绑定记录保留，但不生效
- `DISABLED -> ACTIVE`：恢复 `GRANTED` 绑定的生效状态，不重写历史 `responded_at / joined_at`
- 任意状态下若角色绑定被手工移除，应把 `TenantMemberRole.status` 改为 `REVOKED`
- 任意状态下若重新授予同一角色，只允许复用原记录，将 `REVOKED` 改回 `GRANTED`

### 6.3 字段修复与清理规则

状态迁移时，字段必须同步收敛：

```text
进入 INVITED:
- 必须刷新 invitation_token / invited_by_user_id / invited_at / expires_at
- 必须清空 responded_at
- joined_at 保持为空
- member_no 必须为空

进入 ACTIVE:
- 若来自 `INVITED`，必须清空 invitation_token / invited_by_user_id / invited_at / expires_at，并写入 responded_at / joined_at
- 若来自 `DISABLED`，必须保持历史 responded_at / joined_at 原值不变
- member_no 可为空，可后续补分配

进入 REJECTED:
- 必须清空 invitation_token
- 必须保留 invited_by_user_id / invited_at / expires_at
- 必须写入 responded_at
- joined_at / member_no 必须为空

进入 EXPIRED:
- 必须清空 invitation_token
- 必须保留 invited_by_user_id / invited_at / expires_at
- responded_at / joined_at / member_no 必须为空

进入 REVOKED:
- 必须清空 invitation_token
- 必须保留 invited_by_user_id / invited_at / expires_at
- responded_at / joined_at / member_no 必须为空

进入 DISABLED:
- 必须清空 invitation_token / invited_by_user_id / invited_at / expires_at
- responded_at / joined_at 保留
- member_no 允许保留
```

## 7. 邀请流程

### 7.1 发起邀请

租户管理员邀请一个尚未加入当前租户、但已存在平台账号的人时：

1. 先确认当前 `Tenant.status = ACTIVE`
2. 先确认目标 `User` 已存在，且 `User.status = ACTIVE`
3. 先按 `(tenant_id, user_id)` 查询现有 `TenantMember`
4. 若不存在记录：创建一条新 `TenantMember`，写入 `tenant_id / user_id`，并置为 `status=INVITED`
5. 若已存在 `status=INVITED`：不得再创建第二条记录，必须复用原记录并执行 `resend_invitation`
6. 若已存在 `status=REJECTED / EXPIRED / REVOKED`：不得再创建第二条记录，必须复用原记录并执行 `resend_invitation`
7. 若已存在 `status=ACTIVE`：直接拒绝邀请，因为该用户已经是当前租户成员
8. 若已存在 `status=DISABLED`：不得重新走邀请链路，必须走显式恢复/重新启用流程
9. 若是新建成员记录：明确定义本次预绑定角色列表 `prebound_role_codes[]`
10. 若是新建成员记录：`prebound_role_codes[]` 中的角色必须全部满足 `Role.status = ACTIVE`
11. 生成或刷新 `invitation_token`
12. 写入或刷新 `invited_by_user_id / invited_at / expires_at`
13. 若是新建成员记录：按 `prebound_role_codes[]` 创建对应的 `TenantMemberRole(status=GRANTED)`
14. 若是复用旧成员记录：`resend_invitation` 请求不接收 `prebound_role_codes[]`，默认沿用原有 `GRANTED` 绑定；如需调整角色，必须先显式修改 `TenantMemberRole`，再执行 `resend_invitation`

说明：

- 邀请发送所需的手机号、邮箱等信息从 `StaffProfile` 读取
- `TenantMember` 不重复落这些字段
- `prebound_role_codes[]` 只能选择平台固定角色代码
- `prebound_role_codes[]` 不允许包含 `DISABLED` 的平台角色
- `prebound_role_codes[]` 只用于首次创建邀请态成员
- 复用旧记录重发邀请时，`resend_invitation` 不接收角色列表，沿用 6.2 的角色绑定规则；如需改角色，先显式调整绑定，再执行 `resend_invitation`

### 7.2 接受邀请

接受邀请时：

- 再次确认 `User.status = ACTIVE` 且 `Tenant.status = ACTIVE`
- 按状态迁移规则执行 `INVITED -> ACTIVE`
- 清空 `invitation_token / invited_by_user_id / invited_at / expires_at`
- 填写 `responded_at`
- 填写 `joined_at`
- 如需工号，此时分配 `member_no`

### 7.3 拒绝、过期、撤销、重发

本轮不保留邀请历史，因此都在同一条 `TenantMember` 上处理：

- 拒绝邀请：`status=REJECTED`，清空 `invitation_token`，保留当前这次邀请的 `invited_by_user_id / invited_at / expires_at`，并写入 `responded_at`
- 邀请过期：`status=EXPIRED`，清空 `invitation_token`，保留当前这次邀请的 `invited_by_user_id / invited_at / expires_at`
- 管理员撤销：`status=REVOKED`，清空 `invitation_token`，保留当前这次邀请的 `invited_by_user_id / invited_at / expires_at`
- 重新发送：`status=INVITED`，刷新 `invitation_token / invited_by_user_id / invited_at / expires_at`，并清空 `responded_at`
- `resend_invitation` 不接收角色列表；如需调整角色，必须先修改 `TenantMemberRole`

### 7.4 为什么不支持邀请未注册用户

原因很直接：

- 邀请动作依赖一个已存在的账号主体
- 未创建的 `User` 无法进入当前这套成员关系模型
- “邀请未注册用户”属于注册引导链路，不属于成员邀请链路

## 9. 本版明确不保留的模型

为避免冗余，本版不再保留以下概念：

- `StaffType`
- `SystemRole`
- `TenantMemberPosition`
- `Group`
- `SystemRoleGroup`
- `StaffTypeGroup`

原因：

- `Role` 已承接统一角色层职责
- `RolePermissionGrant` 已直接承接固定角色到固定权限的映射
- `TenantMemberQualification + QualificationType` 已承接业务资质

继续保留上述模型，只会让链路变长、职责重叠、升级漂移更重。

## 10. 后续重构落地方向

后续按本文档重构时，应重点完成：

1. 用平台级 `Role` 替换现有 `SystemRole`
2. 删除 `TenantMemberPosition`
3. 用平台级 `RolePermissionGrant` 替换 `SystemRoleGroup + GroupPermissionScope`
4. 让 `TenantMember` 收敛为纯租户成员关系模型，不重复存 `StaffProfile` 字段
5. 将 `TenantMemberRole` 收敛为“成员绑定平台角色”
6. 将 `TenantMemberRole.status` 收敛为 `GRANTED / REVOKED`
7. 将权限范围收敛为 `ALL / ASSIGNED / OWN`
8. 引入 `QualificationType`，升级 `TenantMemberQualification`
9. 将成员状态迁移矩阵固化到代码
10. 将邀请流程收敛为“已有 `User` 的成员邀请”
11. 将平台固定目录纳入升级/补齐和一致性检查机制
12. 将 `TenantMember` 状态字段矩阵和资质写入校验写成硬规则

## 11. 结论

本版最终收敛结果是：

- `Role` 收敛为平台级角色目录
- 角色统一承载岗位和管理职责
- 角色与权限映射由平台统一定义
- 成员可多角色
- `TenantMemberRole` 只表示成员对平台角色的绑定
- 资质独立建模，并升级为两层结构
- `TenantMember` 只保存租户内关系字段
- 工号放在 `TenantMember`
- `member_no` 默认不可复用
- 邀请前必须已有 `User`
- 邀请状态只保留当前状态，不保留历史
- 成员状态迁移由代码内固定状态机统一约束
- 资质关键字段缺失直接视为无效
- `OWN / ASSIGNED` 只能建立在代码已实现资源判定且历史数据已回填之后
- `is_superuser` 只用于平台级管理，不替代租户成员身份
- `plan_code` 当前不进入授权链

这版模型的目标不是追求抽象完整，而是用最少且自洽的表结构，把“成员-角色-权限”和“成员-资质”两条链彻底理顺，并消除平台升级时的目录漂移问题。
