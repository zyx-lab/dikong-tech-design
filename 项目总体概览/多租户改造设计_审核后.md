# 低空平台多租户改造设计（最终定稿版）

## 1. 目标

将当前系统改造成可对外售卖的 SaaS 多租户系统。

本次定稿只确认以下约束：

1. 不同租户之间的数据必须严格隔离。
2. 买家不能自定义角色，角色由平台统一预置。
3. 每个租户必须有自己的管理角色 `tenant_admin`。
4. 平台默认不能查看租户业务数据。

---

## 2. 总体结论

本系统应改造成：

- 单库共享表的多租户系统
- 所有业务数据显式归属某个 `Tenant`
- 权限采用"平台固定角色 + 租户内分配"
- 平台管理面、租户管理面、业务使用面三层分离

不采用的方案：

- 不采用买家自定义角色
- 不采用每个租户单独一套权限模型
- 不采用平台管理员天然可看所有租户业务数据

---

## 3. 核心原则

### 3.1 租户是一等实体

买家就是 `Tenant`。所有业务数据都必须归属某个租户，不能再依赖零散的组织字段表达租户概念。

### 3.2 租户隔离先于业务权限

所有请求都必须先过租户边界，再进入角色、权限码、scope 判定。

授权顺序应为：

1. 解析当前租户
2. 校验当前用户是否属于该租户
3. 读取该用户在该租户内的固定角色
4. 计算该角色对应的权限与范围
5. 在当前租户内应用 `ALL / OWN / ASSIGNED`

### 3.3 固定角色由平台维护

角色由平台统一定义并初始化，买家只能在本租户内给成员分配固定角色，不能新增或修改角色模板。

### 3.4 平台不进入租户业务数据面

平台只管理租户、套餐、角色模板、权限目录、平台审计和系统运维；默认不能查看租户的业务明细数据。

---

## 4. 管理面划分

### 4.1 平台管理面

面向平台运营方。

**职责**：

- 创建和停用租户
- 初始化租户管理员
- 管理固定角色模板
- 管理全局权限码目录
- 管理套餐、配额、计费
- 查看**平台级审计**（平台操作审计日志，如租户创建、套餐变更、平台配置变更）

**限制**：

- 默认不能查看租户业务数据（无人机、航线、任务、飞行记录、媒体文件等）
- 不能查看**租户级审计**（租户内部操作审计日志，如成员管理、角色分配）

> **审计类型说明**：
> - **平台级审计**：记录平台管理员执行的平台级操作，如租户创建/停用、套餐修改、平台配置变更等。仅平台管理员可查看这些日志。
> - **租户级审计**：记录租户内部治理操作，如成员邀请、角色分配、租户配置变更等。仅租户管理员或业务管理员可在租户内查看这些日志。
> - **业务审计**：记录租户内的业务操作，如无人机创建、任务执行、航线修改等。具有相应权限的业务用户可查看这些日志。

#### 4.1.1 superuser 与 platform_admin 的区分

> **概念区分**：
> - `superuser`：Django 系统级账号，技术概念，拥有所有技术权限（如创建模型、修改权限），**不参与业务权限系统**，不在权限矩阵中体现
> - `platform_admin`：业务角色，用于平台运营管理，受业务权限系统约束

`superuser` 定位：

- Django 技术层面的超级管理员
- 可以绕过业务权限系统进行技术操作
- 用于系统初始化、数据库迁移、紧急修复等技术场景
- **不参与**租户授权链路
- 不在权限矩阵中体现

`platform_admin` 定位：

- 平台运营的业务角色，受业务权限系统约束
- 管理租户账号（开通、停用、配置套餐）
- 管理平台级元数据（角色模板、权限目录）
- 查看平台级审计日志
- **不介入**租户内部事务（成员管理、角色分配、租户审计）
- 不可查看租户业务数据（无人机、航线、任务等）

> **关键区别**：superuser = 技术实现层（绕过业务权限），platform_admin = 业务管理层（受业务权限约束）

---

### 4.2 租户管理面

面向买家管理员，即 `tenant_admin`。

**职责**：

- 管理本租户成员（添加、移除、禁用）
- 给本租户成员分配固定角色
- 查看租户审计（租户级审计日志）
- **管理本租户所有业务数据**（无人机、航线、任务、飞行记录等）
- **是租户最高权限**，可操作租户内一切业务

**限制**：

- 不能访问其他租户
- 不能修改平台角色模板
- 不能修改全局权限码目录

> **说明**：
> - `tenant_admin` 是租户最高权限，包含 `business_admin` 的所有业务权限，并额外拥有租户治理权限（成员管理、角色分配、租户审计）
> - `business_admin`：租户业务管理员，仅管理租户业务数据，无权管理成员和角色分配
> - 两者在业务数据（无人机、航线、任务等）上的权限都是 ALL，区别在于 `tenant_admin` 额外拥有租户治理权限

### 4.3 业务使用面

面向租户内的所有成员（包括各种业务角色）。

**职责**：

- 使用无人机、航线、任务、飞行记录、媒体等业务功能
- 根据固定角色（business_admin / route_planner / dispatcher / pilot_operator / auditor）获取相应业务权限

> **说明**：租户成员 = 租户内的全部人员（广义）。普通业务用户 = 租户成员中承担业务角色的那部分人（狭义，非管理员）。本节面向的是所有租户成员。

## 5. 核心模型

### 5.1 Tenant

租户主表，表示一个买家。

**平台级模型，不需要 tenant_id**。

建议字段：

- `id`
- `code`
- `name`
- `status`
- `plan`
- `created_at`
- `updated_at`

### 5.2 User

平台登录账号，只负责认证。

**平台级模型，不需要 tenant_id**。

#### 5.2.1 StaffProfile 的去留

现有的 `StaffProfile` 保留，作为**用户个人档案**：

- 不参与租户授权逻辑
- 存储用户的个人信息（姓名、工号、手机、邮箱）
- 与租户身份解耦
- 不再是租户成员的身份凭证

> **说明**：原来的 `StaffProfile` 承担了"租户身份"功能。本次改造后，租户身份功能迁移到 `TenantMember`，`StaffProfile` 只保留用户档案功能。

---

### 5.3 TenantMember

表示某个 `User` 在某个 `Tenant` 中的成员身份。

建议字段：

- `id`
- `tenant_id`
- `user_id`
- `display_name`
- `staff_no`
- `phone`
- `email`
- `status`
- `joined_at`
- `created_at`
- `updated_at`

说明：

- `TenantMember` 是租户内身份主体
- 成员管理、角色分配、创建人、指派关系都围绕 `TenantMember`
- 一个 `User` 可以有多个 `TenantMember`（属于不同租户）
- 一个 `TenantMember` 可以绑定多个角色

---

### 5.4 SystemRole

平台固定角色目录。

**平台级模型，不需要 tenant_id**。所有租户共用同一套角色模板。

建议字段：

- `id`
- `code`
- `name`
- `description`
- `status`

### 5.5 TenantMemberRole

租户成员与固定角色的绑定关系。

建议字段：

- `id`
- `tenant_member_id`
- `system_role_id`
- `status`
- `created_at`
- `updated_at`

---

### 5.6 Permission / Group / Scope

以下模型继续保留为**平台级模型**（不需要 tenant_id）：

- `Permission`：权限码定义，全局唯一
- `Group`：能力组，全局唯一
- `GroupPermissionScope`：能力组的作用域定义

绑定关系：

- `SystemRole -> Group`：固定角色关联能力组
- `Group -> Permission`：能力组关联权限码
- `GroupPermissionScope`：定义权限码在什么 scope 下生效

> **说明**：这些是平台级元数据，所有租户共用。授权时，通过 `TenantMember` 找到其绑定的 `SystemRole`，再找到关联的 `Group`，最后根据当前 scope 判定具体权限。

---

## 6. 固定角色

本系统共有 **7 个固定角色（SystemRole）**，由平台统一定义和维护。

> **概念说明**：
> - `superuser`：Django 系统级账号，**不是业务角色**，不在权限矩阵中体现
> - `SystemRole`：平台定义的固定角色模板，所有租户共用

**角色分类**：

| 分类 | 角色 | 说明 |
|-----|------|------|
| 平台级 | `platform_admin` | 平台运营，管理租户 |
| 租户级 | `tenant_admin` | 租户最高权限 |
| 租户级 | `business_admin` | 租户业务管理员 |
| 租户级 | `route_planner` | 航线规划 |
| 租户级 | `dispatcher` | 任务调度 |
| 租户级 | `pilot_operator` | 飞手 |
| 租户级 | `auditor` | 审计查看 |

角色定义：

- `platform_admin`：平台运营角色，管理租户账号、套餐、全局角色模板、权限目录、平台级审计；**不介入租户内部事务**，**不查看租户业务数据**
- `tenant_admin`：租户最高管理角色，管理本租户成员、角色分配、租户级审计和全部业务数据
- `business_admin`：租户内业务管理员，管理本租户全部业务数据（无人机、航线、任务等），但**无权管理成员和角色分配**
- `route_planner`：航线与航点规划
- `dispatcher`：任务调度
- `pilot_operator`：飞行执行
- `auditor`：审计查看

**各角色权限矩阵**：

| 角色 | 平台租户管理 | 成员管理 | 角色分配 | 平台审计 | 租户审计 | 业务审计 | 无人机 | 航线 | 航点 | 任务 | 飞行记录 | 媒体文件 | 无人机分配 |
|-----|:--------:|:--------:|:--------:|:--------:|:--------:|:--------:|:------:|:----:|:----:|:----:|:--------:|:--------:|:----:|
| platform_admin | ALL | - | - | ALL | - | - | - | - | - | - | - | - | - |
| tenant_admin | - | ALL | ALL | - | ALL | ALL | ALL | ALL | ALL | ALL | ALL | ALL | ALL |
| business_admin | - | - | - | - | - | ALL | ALL | ALL | ALL | ALL | ALL | ALL | ALL |
| route_planner | - | - | - | - | - | - | view | manage | manage | - | - | - | - |
| dispatcher | - | - | - | - | - | - | view | - | - | manage | - | - | manage |
| pilot_operator | - | - | - | - | - | - | view | - | - | view | manage | manage | - |
| auditor | - | - | - | - | - | view | view | view | view | view | view | view | - |

> **图例**：
> - `view`：查看权限
> - `manage`：新增/编辑权限
> - `ALL`：全部权限（含查看、新增、编辑、删除）
> - `-`：无权限
>
> **列说明**：
> - **平台租户管理**：平台级租户账号管理（创建/停用租户、配置套餐、设置配额）。这是平台级操作，非租户自助配置。
> - **成员管理**：添加/移除/禁用租户成员（租户内部治理）
> - **角色分配**：给成员分配/撤销角色（租户内部治理）
> - **平台审计**：查看平台级操作审计记录（租户创建、套餐变更、平台配置变更）。详见第 4.1 节。
> - **租户审计**：查看租户治理操作审计记录（成员管理、角色分配、租户配置变更）。详见第 4.1 节。
> - **业务审计**：查看业务操作审计记录（无人机创建、任务执行、航线修改）。详见第 4.1 节。
> - **业务数据列**（无人机、航线、航点、任务、飞行记录、媒体文件、无人机分配）：各业务资源的权限
>
> **说明**：
> - `platform_admin` 只管理租户账号本身，不介入租户内部事务（成员管理、角色分配、租户审计）
> - `auditor` 是租户内部业务角色，可查看业务审计记录和业务数据的查看权限

## 7. 权限体系改造

### 7.1 当前链路

当前系统的授权链是：

`user -> staff_profile -> staff_type -> group -> permission(scope)`

该设计的问题是：

1. 没有租户上下文
2. `staff_type` 同时承担身份类型和权限角色语义
3. 无法表达"租户内分配固定角色"

### 7.2 目标链路

新的授权链应为：

`user -> tenant_member -> tenant_member_role -> system_role -> group -> permission(scope)`

### 7.3 scope 语义

多租户后 scope 定义为：

- `ALL`：当前租户内**全部**数据（可查看、可操作该租户内所有数据）
- `OWN`：当前租户内**自己创建**的数据
- `ASSIGNED`：当前租户内**分配给自己**的数据

> **说明**：scope 定义的是"数据可见范围"，与权限级别（view/manage）是正交关系：
> - 拥有 `view` + `ALL` scope：可查看当前租户内所有数据
> - 拥有 `view` + `OWN` scope：只能查看自己创建的数据
> - 拥有 `manage` + `ALL` scope：可管理当前租户内所有数据

### 7.4 Scope 机制设计

#### 7.4.1 核心原则

**过滤顺序不能颠倒**：

```
1. tenant_id 过滤（强制）→ 2. scope 过滤 → 3. 对象级检查
```

如果顺序颠倒，会导致跨租户数据泄露。

#### 7.4.2 实现方式

```python
# 错误示例（会导致数据泄露）
def get_queryset(self):
    if scope == ScopeType.ALL:
        return queryset  # 危险！返回全部数据（包括其他租户）

# 正确示例
def get_queryset(self):
    # 1. 先过滤租户
    queryset = queryset.filter(tenant_id=current_tenant_id)

    # 2. 再应用 scope
    if scope == ScopeType.ALL:
        return queryset  # 此时 queryset 已经被 tenant_id 过滤过
    if scope == ScopeType.OWN:
        return queryset.filter(created_by_member_id=current_member_id)
    if scope == ScopeType.ASSIGNED:
        return queryset.filter(assigned_member_id=current_member_id)
```

#### 7.4.3 租户上下文结构

```python
@dataclass
class TenantContext:
    tenant_id: int          # 当前租户 ID
    member_id: int          # 当前用户的 TenantMember ID
    roles: list[str]        # 当前用户的角色列表
```

### 7.5 多角色权限计算

一个 `TenantMember` 可以绑定多个 `SystemRole`，权限计算采用**权限取并集**方式。

**计算规则**：

1. 收集当前 TenantMember 绑定的所有角色
2. 合并所有角色的权限（取并集）
3. 合并所有角色的 scope（取最大范围）

**示例**：

```
TenantMember 绑定了: [pilot_operator, route_planner]
- pilot_operator 权限: [view_drone, pilot_mission]，scope: [OWN]
- route_planner 权限: [view_route, manage_route]，scope: [ALL]

最终权限 = 并集 = [view_drone, pilot_mission, view_route, manage_route]
最终 scope = ALL（取最大范围）
```

> **说明**：
> - 如果一个成员既是"飞手"又是"航线规划员"，系统合并两者的权限，使其同时具备两种业务能力
> - scope 取最大范围，确保用户能访问其任一角色有权访问的数据
> - 这种设计避免权限过于复杂，同时满足实际业务需求

## 8. 业务数据模型改造

所有业务核心表都必须显式增加 `tenant_id`：

- `drones`
- `routes`
- `waypoints`
- `missions`
- `flight_records`
- `media_files`
- `drone_assignments`
- `audit_logs`

同时建议统一增加：

- `created_by_member_id`
- `updated_by_member_id`

如存在"指派给谁"的语义，则使用：

- `assigned_member_id`

### 8.1 org_id 与 tenant_id 共存

现有系统中的 `org_id` 字段**保留作为未来扩展字段**：

- 不参与租户隔离逻辑（主要隔离机制是 `tenant_id`）
- 用于未来表达**租户内的组织结构**（如部门、班组、业务单元）
- 未来实现组织级访问控制时，过滤逻辑为：先通过 `tenant_id` 过滤确保租户隔离，再在租户内可选地应用 `org_id` 过滤，实现部门/团队级访问控制
- 组织级访问控制不在本次改造范围内（本次改造聚焦于租户级隔离；组织级访问控制是未来增强功能）

> **示例**：未来租户 A 可以有"北区"、"南区"等组织。当使用 `org_id` 时：
> - 查询 `tenant_id=1, org_id=10` 仅返回租户 1 内组织 10 的数据
> - 查询仅有 `tenant_id=1`（无 org_id）则返回租户 1 内的全部数据
> - 租户隔离始终以 `tenant_id` 作为主要边界强制执行；`org_id` 仅在该租户内提供额外的过滤

---

## 9. 跨表约束

所有跨表引用都必须满足"同租户引用"。

**平台级模型与业务表的关联**：

- 平台级模型（Tenant、User、SystemRole、Permission、Group 等）本身不需要 tenant_id
- 业务表通过外键关联到平台级模型时，必须确保数据属于同一租户

**必须成立的约束包括**：

1. `Mission.route`、`Mission.drone`、`Mission.pilot_member` 必须属于同一 `tenant_id`
2. `FlightRecord.mission`、`FlightRecord.drone`、`FlightRecord.pilot_member` 必须属于同一 `tenant_id`
3. `Waypoint.route` 必须与 `Route` 同租户
4. `MediaFile.flight_record` 必须与 `FlightRecord` 同租户
5. `DroneAssignment.drone` 与 `DroneAssignment.member` 必须同租户

数据库层建议同时保证：

- 所有关键索引包含 `tenant_id`
- 所有唯一约束尽量改为租户内唯一

例如：

- `(tenant_id, code)`
- `(tenant_id, serial_no)`
- `(tenant_id, flight_no)`

## 10. 成员管理机制

### 10.1 账号主权

`User` 账号属于平台，不属于任何租户。

- 账号由平台统一管理
- 租户只能邀请用户加入，不能"创建"账号
- 离职后账号由平台回收或停用

### 10.2 成员加入方式

| 方式 | 说明 | 接口 |
|-----|------|------|
| **邀请制** | 租户管理员发送邀请，用户确认后加入 | `POST /api/access/tenants/{id}/members/invite/` |
| **直接添加** | 租户管理员直接添加已注册用户 | `POST /api/access/tenants/{id}/members/` |

### 10.3 注册与邀请流程

采用**平台注册 + 租户邀请**模式。完整流程为：

```
1. 用户注册 → pending 状态
2. 租户管理员邀请 → 用户收到邀请通知
3. 用户确认邀请 → active 状态，成为租户成员
4. 租户管理员分配角色 → 用户获得业务权限
```

#### 10.3.1 用户注册接口

```json
// POST /api/access/users/register/
{
  "username": "zhangsan",
  "password": "xxx",
  "name": "张三",
  "phone": "13800138000"
}

// 响应
{
  "business_code": "SUCCESS",
  "user_id": 1,
  "message": "注册成功，请等待租户管理员邀请"
}
```

**注册后状态**：

| 状态 | 说明 | 能否登录 | 可访问范围 |
|-----|------|---------|-------------|
| `pending` | 待激活（待租户邀请） | ✓ | 仅可访问平台公共接口（如个人信息修改），不可访问任何租户的业务数据 |
| `active` | 已激活（已加入租户） | ✓ | 可访问所在租户的业务数据（受角色权限约束） |

> **说明**：
> - `pending` 状态的用户已完成平台注册，可以登录平台，但因未加入任何租户，登录后只能访问个人中心等平台级功能
> - 租户管理员邀请并分配角色后，用户状态变为 `active`，即可访问租户业务数据

> **备选流程**：如果租户管理员使用直接添加（无需邀请），用户将自动成为租户成员，无需确认。

## 11. 接口边界

### 11.1 平台接口

职责：

- 租户开通与停用
- 固定角色模板管理
- 权限目录管理
- 平台级审计

### 11.2 租户接口

职责：

- 查看租户级审计（成员管理、角色分配审计日志）
- 成员邀请与管理
- 角色分配

### 11.3 业务接口

保持现有业务域划分，但必须满足：

1. 所有列表、详情、写入都按 `tenant_id` 强制过滤
2. 所有关联对象必须同租户
3. 请求方不能跨租户访问数据

### 12.2 租户上下文传递

**使用 HTTP Header 传递租户上下文**：

```
X-Tenant-Code: tenant_a
```

### 12.3 中间件实现

```python
class TenantContextMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        tenant_code = request.headers.get('X-Tenant-Code')

        if tenant_code:
            tenant = Tenant.objects.filter(code=tenant_code, status=1).first()
            if not tenant:
                raise PermissionDenied("Invalid tenant")
            request.tenant_context = tenant
        else:
            request.tenant_context = None  # 平台接口

        return self.get_response(request)
```

### 12.4 View 层使用

```python
class DroneViewSet(...):
    def get_queryset(self):
        tenant = getattr(self.request, 'tenant_context', None)
        if tenant:
            return super().get_queryset().filter(tenant_id=tenant.id)
        # 无租户上下文 = 平台接口（如租户管理）
        return super().get_queryset()
```

## 13. 租户守卫机制

### 13.1 为什么需要

开发者可能会忘记在新建数据时传入 `tenant_id`，导致数据"无主"或跨租户污染。

### 13.2 TenantGuardMixin 实现

使用显式约束，确保数据必须有 tenant_id：

```python
class TenantGuardMixin:
    """租户守卫：确保所有业务数据必须归属某个租户"""

    tenant = models.ForeignKey('access.Tenant', on_delete=models.PROTECT)

    def save(self, *args, **kwargs):
        if not self.tenant_id:
            raise ValidationError("tenant_id is required")
        super().save(*args, **kwargs)

    def clean(self, *args, **kwargs):
        if not self.tenant_id:
            raise ValidationError("tenant_id is required")
        super().clean(*args, **kwargs)
```

**使用示例**：

```python
class Drone(TenantGuardMixin, models.Model):
    code = models.CharField(max_length=64)
    name = models.CharField(max_length=128)
    # ... 其他字段
```

## 14. 对当前系统的改造方向

### 需要保留的部分

- 现有权限码目录（Permission 模型）
- `Group` 能力组思想
- `GroupPermissionScope` 作用域定义
- `ALL / OWN / ASSIGNED` scope 机制
- 业务 View 到权限码的映射方式

### 需要重构的部分

| 当前模型 | 改造方向 | 说明 |
|---------|---------|------|
| `StaffProfile` | 保留为用户个人档案 | 仅存储用户个人信息，不再参与租户授权逻辑 |
| `StaffType` | 废弃 | 原为租户内身份类型，本次改造后不再需要 |
| `SystemRole`（新增） | 平台固定角色目录 | 跨所有租户的固定角色模板，由平台统一维护 |
| `TenantMember`（新增） | 租户成员身份 | 替代原 StaffProfile 的租户身份功能 |
| 授权服务 | 基于 `TenantMember` 重新实现 | 授权链路：user -> tenant_member -> tenant_member_role -> system_role -> group -> permission(scope) |
| 所有业务模型 | 补足 `tenant_id` | 显式归属租户 |
| 所有业务查询 | 默认租户过滤 | 强制 tenant_id 过滤 |
| 所有业务写入 | 强制同租户校验 | 关联对象必须同租户 |

## 15. 实施顺序

建议按以下顺序推进：

1. 引入 `Tenant`
2. 重构成员模型为 `TenantMember`
3. 固化平台固定角色模型，并加入 `tenant_admin`
4. 所有业务表补 `tenant_id`
5. 重写授权链为"当前租户内授权"
6. 拆分平台管理面与租户管理面
7. 增加数据库级租户隔离

## 16. 最终结论

本系统的最终多租户形态应为：

- 平台固定角色
- 租户内成员分配角色
- `tenant_admin` 负责租户治理
- 平台默认不可见租户业务数据
- 所有业务数据显式归属租户
- 所有权限先过租户边界，再做角色与 scope 判定

一句话总结：

本系统应从"单组织权限系统"升级为"平台管租户、租户管成员、业务数据强隔离"的 SaaS 多租户系统。
