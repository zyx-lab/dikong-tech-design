# 业务注册申请与审核系统设计（V1）

本文档定义业务侧“注册申请”能力，目标是满足以下规则：
1. 用户注册时只提交基础信息 + 期望 `staff_type`（申请值）。
2. 系统把它记为“待审核申请”，不给业务权限。
3. 管理员在 IAM 审核通过后，才创建/激活正式账号并绑定真实 `staff_type`。
4. 审核通过后用户才能登录业务界面。

---

## 1. 设计目标

1. 提供对外可用的注册入口，但不破坏现有授权模型。
2. 保持“授权只走 IAM”原则，避免业务侧绕过。
3. 实现“先申请，后审批，再开户”的闭环。
4. 全链路可审计、可追溯、可拒绝。

---

## 2. 架构边界

1. 业务平面（`/api/v1/*`）
- 提供注册申请接口。
- 只写“申请单”，不创建正式业务账号。

2. IAM 平面（`/internal/auth/*`）
- 提供审核与开户接口。
- 负责把申请转成 `User + StaffProfile + StaffType`。

3. superuser 职责
- 作为 root 账号，默认拥有系统与业务全量权限。
- 仅允许命令行创建，不在 Admin/API 中升权。

---

## 3. 角色与职责

1. 申请人（未登录用户）
- 提交注册申请。
- 查询自己申请状态。

2. 审核员（IAM 管理员）
- 查看待审核申请。
- 审核通过/驳回。
- 审核通过时触发开户。

3. 系统
- 校验申请数据与重复性。
- 记录申请状态流转与审计日志。

---

## 4. 核心流程

1. 申请人提交注册申请：
- 输入：姓名、手机号、邮箱、期望 `staff_type_code`、备注。
- 输出：`application_no`（申请单号）与初始状态 `PENDING_REVIEW`。

2. 审核员在 IAM 查看申请：
- 可校验身份材料、组织归属、岗位真实性。

3. 审核通过：
- 系统创建正式业务账号（`is_superuser=False`）。
- 创建 `StaffProfile`，绑定审核后的真实 `staff_type`。
- 审核接口请求体显式提交 `username`、`password`、`staff_no`。
- 申请状态变更为 `APPROVED_ACCOUNT_CREATED`。

4. 审核驳回：
- 记录驳回原因。
- 申请状态变更为 `REJECTED`。

5. 申请人收到结果：
- 通过后可登录业务系统并按角色权限访问。
- 驳回后可重新提交新申请。

---

## 5. 状态机设计

建议状态枚举：
1. `PENDING_REVIEW`：待审核
2. `APPROVED_ACCOUNT_CREATED`：已通过并完成开户
3. `REJECTED`：已驳回

状态流转：
1. `PENDING_REVIEW -> APPROVED_ACCOUNT_CREATED`
2. `PENDING_REVIEW -> REJECTED`

不可逆规则：
1. `APPROVED_ACCOUNT_CREATED` 不可再改为 `PENDING_REVIEW`。
2. `REJECTED` 不可直接转“通过”，需新建申请单。

---

## 6. 数据模型设计

建议新增表：`registration_applications`

字段：
1. `id`
2. `application_no`：唯一申请号
3. `name`
4. `phone`
5. `email`
6. `requested_staff_type_code`：申请值
7. `requested_org_id`：申请组织（可选）
8. `status`
9. `reviewer_user_id`：审核人
10. `reviewed_at`
11. `review_comment`：驳回或审核备注
12. `created_user_id`：通过后创建的 `User`（可空）
13. `created_staff_id`：通过后创建的 `StaffProfile`（可空）
14. `created_at` / `updated_at`

约束建议：
1. 同手机号在 `PENDING_REVIEW` 状态下只能有 1 条申请。
2. 同邮箱在 `PENDING_REVIEW` 状态下只能有 1 条申请。
3. `requested_staff_type_code` 必须在“可申请列表”内（`StaffType.is_registrable=True`）。

---

## 7. API 设计

### 7.1 业务平面（对申请人）

1. `POST /api/v1/registration-applications`
- 新建申请
- 不要求登录
- 请求体：`name/phone/email/requested_staff_type_code`（`requested_org_id/application_note` 可选）

2. `GET /api/v1/registration-applications/{application_no}/status`
- 查询申请状态

### 7.2 IAM 平面（对审核员）

1. `GET /internal/auth/registration-applications`
- 列表与筛选（状态、手机号、申请时间）

2. `GET /internal/auth/registration-applications/{id}`
- 申请详情

3. `POST /internal/auth/registration-applications/{id}/approve`
- 审核通过并开户
- 必填：`username/password/staff_no`
- 可选：`final_staff_type_code/final_org_id/review_comment`

4. `POST /internal/auth/registration-applications/{id}/reject`
- 审核驳回
- 必填驳回原因

---

## 8. 权限设计

新增 IAM 权限码建议：
1. `access.view_registration_application`
2. `access.manage_registration_application`

默认矩阵建议：
1. `ops_admin`（Admin管理员）：查看 + 审核
2. 其他角色：默认不授予

注意：
1. 申请人侧接口不走业务角色权限，只走防滥用与数据校验。
2. 审核动作必须走 IAM 权限，不允许业务接口直接开户。

---

## 9. 审计与合规

审计动作建议：
1. `REGISTRATION_APPLICATION_CREATE`
2. `REGISTRATION_APPLICATION_APPROVE`
3. `REGISTRATION_APPLICATION_REJECT`
4. `REGISTRATION_ACCOUNT_CREATE`

每条审计至少记录：
1. `actor_user`
2. `target_type=registration_application/user/staff_profile`
3. `target_id`
4. `before_data/after_data`
5. `request_id/ip`

---

## 10. 安全与风控

1. 防枚举：
- 状态查询接口不要暴露完整用户信息。
- 错误提示避免泄露“手机号是否已存在账号”。

2. 账号安全：
- 审核通过时由 IAM 审核员显式设置开户 `username/password`。

3. 数据保护：
- 手机/邮箱展示脱敏。
- 审核备注仅 IAM 可见。

---

## 11. 与现有系统的衔接

1. 不改变现有核心授权链：`StaffType -> Group -> Permission + Scope`。
2. 仅在“账号来源”层新增申请流程。
3. superuser 规则：默认拥有全量权限，不走 staff_type 授权链。
4. “业务管理员账号”仍使用普通业务账号 + `business_admin`，可由审核流程或管理命令创建。

---

## 12. 分阶段落地建议

阶段 1（最小可用）：
1. 落 `registration_applications` 表。
2. 提供申请创建接口 + IAM 审核通过/驳回接口。
3. 审核通过时调用现有开户逻辑创建 `User + StaffProfile`。

阶段 2（增强）：
1. 增加申请补充材料上传。
2. 增加风控规则与反作弊策略。

阶段 3（运营化）：
1. 审核 SLA 看板。
2. 批量审核与导入。
3. 审计报表导出。
