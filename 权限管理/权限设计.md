# 低空平台用户权限系统设计

## 1. 设计目标与边界
1. 本系统用于平台内部用户权限管理，不对外公开。
2. 采用 RBAC（Role-Based Access Control）模型，并叠加数据范围控制。
3. 身份信息与授权信息分离管理。

## 2. 总体规则

### 2.1 身份与权限分离
1. `auth_users`  
用于登录认证与账号状态控制（是否可登录）。
2. `staff_profiles`  
用于人员身份与业务属性（姓名、组织归属、在职状态、岗位类型）。
3. `roles + permissions + scopes`  
用于授权（能做什么、能看哪些数据）。

### 2.2 授权核心定义
1. `permission`：最小可判定操作，如 `missions:start`、`routes:update`、`media_files:export`。
2. `role`：权限集合，如 `dispatcher` 包含任务创建、分配、启动、暂停等权限。
3. 一个用户可拥有多个角色；一个角色可分配给多个用户。
4. 数据范围 `scope` 是“某角色对某权限”的范围属性，取值：`ALL/OWN/ASSIGNED`。
5. 完整授权关系由元组集合定义：`(role_id, permission_id, scope_type)`。

## 3. 权限判定公式
`允许 = 账号/人员状态通过 AND 角色权限通过 AND 数据范围通过 AND 业务状态机条件通过`

说明：
1. 账号/人员状态：账号禁用、离职、资质失效等场景直接拒绝。
2. 角色权限：用户是否拥有目标权限点。
3. 数据范围：在有权限前提下，是否命中可见/可操作数据。
4. 业务状态机：例如任务状态不允许 `start/pause` 时拒绝。

## 4. 最终表设计

| 表名 | 核心字段（建议） | 说明 |
|---|---|---|
| `auth_users` | `id, username(unique), password_hash, status, last_login_at, failed_login_count, locked_until, created_at, updated_at` | 登录账号主体 |
| `staff_profiles` | `id, staff_no(unique), name, phone, email, employment_status, position_type, org_id, created_at, updated_at` | 人员通用档案 |
| `pilot_profiles` | `id, staff_id(unique fk), license_level, medical_expiry_at, total_flight_hours, created_at, updated_at` | 飞手子档案（专业字段） |
| `route_planner_profiles` | `id, staff_id(unique fk), planner_level, created_at, updated_at` | 规划员子档案（按需） |
| `staff_certifications` | `id, staff_id fk, cert_type, cert_no, issued_at, expires_at, status, created_at, updated_at` | 通用资质档案（执照/证书） |
| `auth_user_staff_bindings` | `id, user_id fk, staff_id fk, is_primary, status, valid_from, valid_to, created_at, updated_at` | 账号-人员绑定 |
| `auth_roles` | `id, code(unique), name, description, status, is_system, created_at, updated_at` | 角色模板 |
| `auth_permissions` | `id, code(unique), resource, action, name, description, status, created_at, updated_at` | 权限点字典（如 `missions:start`） |
| `auth_user_roles` | `id, user_id fk, role_id fk, status, granted_by_user_id, granted_at, expires_at, created_at, updated_at` | 用户角色分配 |
| `auth_role_permission_scopes` | `id, role_id fk, permission_id fk, scope_type(ALL/OWN/ASSIGNED), status, created_at, updated_at` | 角色-权限-数据范围 |
| `auth_audit_logs` | `id, actor_user_id, action, target_type, target_id, before_data(jsonb), after_data(jsonb), ip, request_id, created_at` | 授权与关键动作审计 |

## 5. 关键约束
1. `auth_user_roles`：`UNIQUE(user_id, role_id)`。
2. `auth_role_permission_scopes`：`UNIQUE(role_id, permission_id)`。
3. `auth_permissions`：`UNIQUE(resource, action)`（强烈建议）。
4. `auth_user_staff_bindings`：`UNIQUE(user_id, staff_id)`。
5. 同一用户同一时刻仅允许 1 条有效主绑定（`is_primary=true` 且 `status=1`）。

## 6. 数据范围定义（V1）
1. `ALL`：全量数据。
2. `OWN`：`created_by_staff_id = 当前staff_id`。
3. `ASSIGNED`：命中分配关系的数据。

业务落地前提：
1. 需要支持 `OWN` 的业务表必须具备 `created_by_staff_id`。
2. 需要支持 `ASSIGNED` 的资源必须有明确分配关系。  
例如：`mission_assignees(mission_id, staff_id, assignment_role, status, assigned_at)`。

## 7. 初始角色（V1）
1. `super_admin`：全权限 + 全范围。
2. `ops_admin`：业务管理全权限（非超管项可限制）。
3. `route_planner`：航线/航点维护（以 `OWN` 为主）。
4. `dispatcher`：任务编排与调度（多为 `ALL`）。
5. `pilot_operator`：执行类权限（多为 `ASSIGNED`）。
6. `auditor`：只读/导出（`ALL`）。

## 8. 命名规范
1. `auth_roles.code`：角色机器标识，如 `dispatcher`、`pilot_operator`。
2. `auth_permissions.code`：权限机器标识，格式 `resource:action`，如 `missions:start`。
3. `code` 一旦发布应保持稳定，避免频繁变更。
