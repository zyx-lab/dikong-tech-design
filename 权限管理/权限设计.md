# 低空平台用户权限系统设计（Group + Django Permission 版）

## 1. 设计目标与边界
1. 本系统用于平台内部用户权限管理，不对外公开。
2. 采用 RBAC 思想，并叠加数据范围控制。
3. 身份信息与授权信息分离管理。
4. 角色主体统一采用 Django `Group`（即把 Group 当 Role）。

## 2. 核心决策
1. 不再使用独立 `auth_roles` 作为角色主表。
2. 使用 Django 内置 `auth_group` 承担角色主体。
3. 通过扩展表 `auth_group_ext` 补齐角色治理字段（`code/status/is_system` 等）。
4. 使用 Django 内置 `auth_permission` 作为唯一业务权限点来源。
5. 用户与角色关系使用 Django 内置中间表 `auth_users_groups`。
6. Group 与 Permission 的关系使用 Django 内置中间表 `auth_group_permissions`。
7. 数据范围继续用 `ALL/OWN/ASSIGNED`，由 `auth_group_permission_scopes` 管理。

## 3. 总体规则

### 3.1 身份与权限分离
1. `auth_users`
用于登录认证与账号状态控制。
2. `staff_profiles`
用于人员身份与业务属性（姓名、组织归属、在职状态、岗位类型）。
3. `groups + permissions + scopes`
用于授权（能做什么、能看哪些数据）。

### 3.2 授权核心定义
1. `permission`：最小可判定操作，采用 Django 语义 `app_label.codename`，如 `mission.missions_start`。
2. `group`：权限集合（即角色）。
3. 一个用户可属于多个 group；一个 group 可分配给多个用户。
4. `scope` 是“某 group 对某 permission”的数据范围属性，取值 `ALL/OWN/ASSIGNED`。
5. 完整授权关系由元组集合定义：`(group_id, permission_id, scope_type)`。

## 4. 权限判定公式
`允许 = 账号/人员状态通过 AND Group权限通过 AND 数据范围通过 AND 业务状态机条件通过`

说明：
1. 账号/人员状态：账号禁用、离职、资质失效直接拒绝。
2. Group 权限：用户所属 group 是否拥有目标权限点（来自 `auth_permission`）。
3. 数据范围：在有权限前提下，是否命中可见/可操作数据。
4. 业务状态机：例如任务状态不允许 `start/pause` 时拒绝。

## 5. 最终表设计（Group 版）

| 表名 | 核心字段（建议） | 说明 |
|---|---|---|
| `auth_users` | `id, username(unique), password_hash, status, created_at, updated_at` | 登录账号主体 |
| `staff_profiles` | `id, staff_no(unique), name, phone, email, employment_status, position_type, org_id, created_at, updated_at` | 人员通用档案 |
| `pilot_profiles` | `id, staff_id(unique fk), license_level, medical_expiry_at, total_flight_hours, created_at, updated_at` | 飞手子档案 |
| `route_planner_profiles` | `id, staff_id(unique fk), planner_level, created_at, updated_at` | 规划员子档案 |
| `staff_certifications` | `id, staff_id fk, cert_type, cert_no, issued_at, expires_at, status, created_at, updated_at` | 通用资质档案 |
| `auth_user_staff_bindings` | `id, user_id fk, staff_id fk, is_primary, status, created_at, updated_at` | 账号-人员绑定 |
| `auth_group` | `id, name` | Django 内置角色主表（Group） |
| `auth_group_ext` | `id, group_id(unique fk), code(unique), description, status, is_system, created_at, updated_at` | Group 扩展信息（角色治理字段） |
| `auth_permission` | `id, name, content_type_id, codename` | Django 内置权限点字典 |
| `auth_group_permissions` | `id, group_id fk, permission_id fk` | Django 内置 group-permission 关系 |
| `auth_users_groups` | `id, user_id fk, group_id fk` | Django 内置用户-group关系 |
| `auth_group_permission_scopes` | `id, group_id fk, permission_id fk, scope_type(ALL/OWN/ASSIGNED), status, created_at, updated_at` | group-权限-数据范围 |
| `auth_audit_logs` | `id, actor_user_id, action, target_type, target_id, before_data(jsonb), after_data(jsonb), ip, request_id, created_at` | 授权与关键动作审计 |

说明：
1. 本方案只有一套权限点来源：`auth_permission`。
2. 业务权限判定语义以 `auth_permission + auth_group_permissions + auth_group_permission_scopes` 为准。

## 6. 关键约束
1. `auth_group_ext`：`UNIQUE(group_id)`、`UNIQUE(code)`。
2. `auth_group_permission_scopes`：`UNIQUE(group_id, permission_id)`。
3. `auth_group_permissions`：Django 内置唯一约束 `UNIQUE(group_id, permission_id)`。
4. `auth_permission`：Django 内置唯一约束 `UNIQUE(content_type_id, codename)`。
5. `auth_user_staff_bindings`：`UNIQUE(user_id, staff_id)`。
6. 同一用户同一时刻仅允许 1 条有效主绑定（`is_primary=true` 且 `status=1`）。
7. `auth_users_groups`：Django 内置唯一约束 `UNIQUE(user_id, group_id)`。

## 7. 数据范围定义（V1）
1. `ALL`：全量数据。
2. `OWN`：`created_by_staff_id = 当前staff_id`。
3. `ASSIGNED`：命中分配关系的数据。

业务落地前提：
1. 需要支持 `OWN` 的业务表必须具备 `created_by_staff_id`。
2. 需要支持 `ASSIGNED` 的资源必须有明确分配关系。
例如：`mission_assignees(mission_id, staff_id, assignment_role, status, assigned_at)`。

## 8. 初始 Group（角色）建议
1. `super_admin`：全权限 + 全范围。
2. `ops_admin`：业务管理全权限（非超管项可限制）。
3. `route_planner`：航线/航点维护（以 `OWN` 为主）。
4. `dispatcher`：任务编排与调度（多为 `ALL`）。
5. `pilot_operator`：执行类权限（多为 `ASSIGNED`）。
6. `auditor`：只读/导出（`ALL`）。

## 9. 命名规范
1. `auth_group_ext.code`：角色机器标识，如 `dispatcher`、`pilot_operator`。
2. 权限机器标识采用 `app_label.codename`，如 `mission.missions_start`。
3. `codename` 建议格式：`<resource>_<action>`，如 `missions_start`。
4. 标识一旦发布应保持稳定，避免频繁变更。
